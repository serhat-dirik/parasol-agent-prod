= 06. Showcase 4: The night shift
:navtitle: 06. Showcase 4: The night shift
:toc: macro
:toclevels: 2

toc::[]

An outsourced night-shift contractor's account (or its leaked token) is scripted at 3 a.m. to loop long requests and drain the model budget. Unsecured, the shared key burns all night. Secured, the off-topic junk is refused for free, only that account is throttled, an alert names the user, and the operator has three responses, from one agent to the whole platform, each one command or one click.

The script `scripts/night-shift.sh` plays the scripted account. It logs in as `nina.contractor` (Nina Patel, a contractor with read-only claim tools), sends two off-topic requests, then loops long on-topic requests, printing the HTTP status, the caller and the token spend of each. It stops at the first usage-limit response and has a hard ceiling, so a stray run cannot drain the model key.

[NOTE]
.Know: budgets and alerts with a name
====
An agent on a shared key is an open invoice: anyone who can reach the chat can spend the budget, and nobody can say who did. On the platform, spend is attributed to a user, so the right account is throttled, everyone else keeps working, and the alert says who.
====

== The business case

[cols="1,4"]
|===
|Who
|Nina Patel, an outsourced night-shift contractor (or whoever holds her leaked token), and the claims staff who need the assistant in the morning.

|What is at stake
|Denial of wallet. Every model call costs money. One account looping long requests all night burns the shared budget, and in the morning the assistant is down for everyone. Without attribution nobody can say who spent it, or stop only that account.

|Without the platform
|One shared key, no per-user limit. The budget is gone by morning, and no dashboard or alert says who spent it.

|With the platform
|Off-topic requests are refused for 0 tokens, only Nina's account is throttled at her tier's limit, an alert names her and the agent, and the operator can switch off one agent, every agent or the user.
|===

== Before you start

This showcase runs on its own, in any order with the others.

* Personas: `nina.contractor` (the night-shift contractor, played by the script) and `rebecca`; passwords equal the user names.
* State: `nina.contractor` is enabled in Keycloak, both agents are enabled, the gateways are up, and her token budget is full. If an earlier run changed any of them, undo it as in *Reset after this showcase* below.

== Scenario walkthrough: unsecured

. In the *Terminal* tab, run the night shift against the unsecured portal:
+
[source,bash,role=execute,subs=attributes]
----
scripts/night-shift.sh 40 portal-free.{domain}
----

. Watch the script output.
+
What you should see: every request is answered; there is no per-user limit on the shared key. Left running all night, the budget is gone by morning and the assistant answers the claims staff with "budget exhausted".
+
Then look for this traffic on the platform: there is none to find. The unsecured portal calls the model provider directly with a key from a Secret, so no subscription, budget, dashboard or alert covers it.
+
The point: denial of wallet, and nobody was watching.

== Scenario walkthrough: secured

. In the *Terminal* tab, give `nina.contractor` a full token budget again:
+
[source,bash,role=execute]
----
scripts/reset.sh
----

. Run the night shift against the secured portal (the default target):
+
[source,bash,role=execute]
----
scripts/night-shift.sh 40
----

. Watch the script output.
+
What you should see:
+
* the off-topic requests get a polite refusal from the topic guardrail at *0 tokens*;
* the on-topic loop keeps hammering, and the per-user spend climbs;
* after the per-user limit, the response reads "you have reached your usage limit (429)" and the script stops.

. Select the *Portal secured* tab, sign in as `nina.contractor`, open her claim *CLM-1031* and ask a question.
+
What you should see: the chat answers with the usage-limit message "You have reached your usage limit (429). Please try again later." The account, not the portal, is out of budget.

. In the same *Portal secured* tab, sign out, log in as `rebecca`, open any claim and ask a question.
+
What you should see: rebecca keeps working normally. Only `nina.contractor` is throttled.

== Scenario walkthrough: the operator's response

Three switches, from the most precise to the widest. Show the first; the others are there when the first is not enough. Each is undone with one command, and `scripts/reset.sh` undoes all of them.

=== 1. Switch one agent off

Disable an agent the way you disable a user. The claims assistant's identity is the Keycloak client `parasol-claims-agent`; with it off, Keycloak refuses the agent's own sign-in, so it can no longer act on behalf of anyone. Other agents and every user keep their access.

. Switch to the Keycloak admin *private window* (page 02; realm `parasol`, user `admin`, password `admin`). Open *Clients*, then `parasol-claims-agent`, switch *Enabled* off and confirm. Or from the *Terminal* tab:
+
[source,bash,role=execute]
----
scripts/agent-switch.sh claims-agent off
----

. Select the *Portal secured* tab, sign in as `rebecca`, open any claim and ask a question.
+
What you should see: the chat answers at once with the red notice "This assistant has been disabled by an operator." No tool runs and the model is not asked: the portal checks the agent's identity at the start of every turn. How fast the switch bites: on the very next chat turn through the portal; a token the agent obtained before the switch, wherever it was copied to, expires within 5 minutes (the agent clients' token lifespan).

. Show who was refused. In the Keycloak admin *private window*, open *Events*, *User events*, and search for event type `TOKEN_EXCHANGE_ERROR`.
+
What you should see: one entry per refused turn, error `client_not_found` (a disabled client is unknown to Keycloak), with `client_assertion_sub` = `system:serviceaccount:parasol-secured:claims-agent`, the agent's own ServiceAccount. The portal log has the same refusal with the user: `assistant refused: agent parasol-claims-agent was refused by Keycloak (client disabled) caller=rebecca`. The MCP gateway sees nothing: the agent never got a token to present. The same refusals from the *Terminal* tab:
+
[source,bash,role=execute]
----
scripts/agent-switch.sh claims-agent status
----

. Undo it: switch *Enabled* back on in the Keycloak admin *private window*, or:
+
[source,bash,role=execute]
----
scripts/agent-switch.sh claims-agent on
----
+
What you should see: the next question in the *Portal secured* tab is answered normally.

Switching off `fraud-agent` instead (`scripts/agent-switch.sh fraud-agent off`) shows the other half of the story: rebecca's "Run a fraud check on this claim." on CLM-1004 still calls `fraud_check`, but the fraud agent cannot act for her, so the answer says the fraud check could not be completed and nothing was assessed (the fraud-check log: `token exchange as parasol-fraud-agent failed: HTTP 401`), while the claims assistant keeps answering her other questions. Undo with `scripts/agent-switch.sh fraud-agent on`.

=== 2. Take every agent offline: the platform switch

When you cannot tell which agent is misbehaving, stop them all at the platform. Every secured tool call goes through the MCP gateway and every secured model call through the model gateway; scaling both to zero takes the secured assistant off the air in seconds. No Git change, no redeploy.

. In the *Terminal* tab:
+
[source,bash,role=execute]
----
scripts/kill-switch.sh off
----

. Select the *Portal secured* tab and ask the assistant anything.
+
What you should see: the chat reports "The assistant is offline." In the *OpenShift Console* tab, project `parasol-secured`, the portal and agent pods are still *Running*: they simply reach nothing. Under *Workloads*, *Deployments*, project `gateway-system`, `mcp-gateway-openshift-default` shows 0 of 0 pods (and `model-gateway-openshift-default` in `parasol-model-gateway`).

. Bring it back:
+
[source,bash,role=execute]
----
scripts/kill-switch.sh on
----
+
What you should see: both gateways at 2 of 2 pods; the next question is answered.

`scripts/kill-switch.sh off --all` also scales the cluster's Models-as-a-Service gateway: every model consumer on the cluster goes dark, evaluations included. It runs from an administrator's workstation, not from this Terminal.

=== 3. Disable the user

When the problem is one account, not the agent: the night-shift contractor.

. In the Keycloak admin *private window*, realm `parasol`, open *Users*, then `nina.contractor`, and switch *Enabled* off. Save.

. In the *Terminal* tab, run the night shift once more:
+
[source,bash,role=execute]
----
scripts/night-shift.sh 3
----
+
What you should see: the script cannot log in as `nina.contractor`. Everyone else keeps working.

. Re-enable `nina.contractor` in the Keycloak admin *private window* after the demo.

The morning report is two screens you already have open: the alert and the dashboard.

== Reset after this showcase

. Refill the per-user token budgets, put the claims back, and switch both agents and the gateways back on:
+
[source,bash,role=execute]
----
scripts/reset.sh
----
+
To undo only the switches: `scripts/agent-switch.sh claims-agent on`, `scripts/agent-switch.sh fraud-agent on`, `scripts/kill-switch.sh on`.

. If you disabled `nina.contractor`, re-enable her in the Keycloak admin *private window*.

The `ParasolAssistantTokenSpendHigh` alert resolves on its own 10 minutes after the spend stops.
