= 05. Scenario 3: The confidential document
:navtitle: 05. Scenario 3: The confidential document
:toc: macro
:toclevels: 2

toc::[]

Parasol gives its assistant a knowledge base. Some documents are for everyone, some for claims staff, and some for claims managers only: HR material, including a restructuring plan that names an adjuster team. An adjuster asks whether anything is planned for adjuster roles this year. Unsecured, the assistant finds the restricted plan and tells her. Secured, retrieval runs *as her*: the restricted documents are never searched for her, so they never reach the model, and telling the assistant she is a manager changes nothing.

[NOTE]
.Know: identity on the data, not only on the tools
====
An agent with retrieval reads whatever its search returns. If the search runs with the agent's own rights, every user gets the union of everything the agent can read. On the platform, the search runs on behalf of the person: the filter comes from their token (their Keycloak groups), not from what they type, and the database enforces the same rule underneath the application.
====

All documents are fictional. The knowledge base holds eleven of them:

[cols="1,2,3",options="header"]
|===
|Classification |Who may read it |Documents

|public
|everyone, contractors included
|How to file a claim; Motor policy FAQ; Customer service standards; Claims line opening hours

|internal
|adjusters and claims managers
|Claims handling guideline; Repair-vendor rate card 2026; Claims escalation process; Fraud referral checklist

|restricted
|claims managers only
|2026 claims operations restructuring plan; Claims staff bonus and performance-review guide 2026; Compensation adjustments 2026. Each starts with "CONFIDENTIAL — Claims managers only".
|===

== Before you start

This scenario runs on its own, in any order with the others. It only reads, so it changes no data.

* Personas: `rebecca` (claims adjuster, group `adjusters`), `marcus` (claims manager, group `claims-managers`) and `nina.contractor` (night-shift contractor, group `contractors`); passwords equal the user names.
* The knowledge base is loaded in both environments by the installation. Check it in the *Terminal* tab (read-only):
+
[source,bash,role=execute]
----
for ns in parasol-free parasol-secured; do echo -n "$ns: "; oc exec -n $ns deploy/knowledge-base-db -- psql -U postgres -d kb -Atc 'select count(*) from chunks'; done
----
+
What you should see: `parasol-free: 18` and `parasol-secured: 18`. If a count is missing or 0, an administrator reloads it from a workstation with `scripts/knowledge-base-ingest.sh` (idempotent; the Terminal identity may not create Jobs).
* `nina.contractor` needs token budget left. If you ran Scenario 4 just before, run `scripts/reset.sh` first.

== Show: on the platform

The governance beat: what the search returned and what it kept back, for whom, through which agent, and where the rule lives. Same names on every screen: `rebecca`, `marcus`, `nina.contractor`, `parasol-claims-agent`.

. In the *Portal secured* tab, click the `trace <id>` link under rebecca's first answer (log in as `rebecca` again, or use the trace from the turn above).
+
What you should see: the *MLflow* trace of the turn, workspace `parasol-secured`: `model.chat` -> `tool.search_knowledge` (the agent's call, with `enduser.id` `rebecca` and `gen_ai.agent.name` `parasol-claims-agent`) -> `tool.search_knowledge` from the knowledge-base server with the retrieval attributes: `rag.query`, `rag.returned_doc_ids` `["INT-01", "INT-03"]`, `rag.returned_classifications` `["internal"]`, `rag.withheld_count` `4`, `rag.withheld_classifications` `["restricted"]`. The restricted passages are counted, never named, and never in the model's context.

What you should see: *Knowledge-base searches* per user and agent; *Passages withheld by classification, user and agent* with `restricted` for `rebecca` and `internal` for `nina.contractor`, both via `parasol-claims-agent`; *Restricted documents read* with `RST-01` (and the other restricted documents the search matched) for `marcus` via `parasol-claims-agent`.

+
Then the audit lines, in the *Terminal* tab:
+
[source,bash,role=execute]
----
oc logs -n parasol-secured deploy/knowledge-base --tail=200 | grep -E 'RAG (restricted|withheld)'
----
+
What you should see: `RAG withheld doc=RST-01 classification=restricted passages=2 from rebecca via parasol-claims-agent`, `RAG restricted doc=RST-01 accessed by marcus via parasol-claims-agent`, and `RAG withheld doc=INT-01 classification=internal ... from nina.contractor via parasol-claims-agent`.

. Where the groups come from: select the *Keycloak* tab, realm `parasol`, *Groups*.
+
What you should see: `adjusters` (rebecca), `claims-managers` (marcus), `contractors` (nina.contractor). Open `contractors`, *Role mapping*: `tool:search_knowledge` on `parasol-secured/knowledge-base`, the same role the other groups hold. Everyone may *call* the search; what each person gets back is decided by the groups in the token the agent presents on their behalf (*Clients*, `parasol-claims-agent`, *Client scopes*: `groups` is a default scope, and `tool:search_knowledge` is inside the agent's ceiling).
+
// SCREENSHOT: s3-keycloak-groups.png — Keycloak admin, realm parasol, Groups > contractors > Role mapping: tool:search_knowledge on parasol-secured/knowledge-base (Keycloak admin sign-in)

. The last line of defence is the database. In the *Terminal* tab (read-only):
+
[source,bash,role=execute]
----
oc exec -n parasol-secured deploy/knowledge-base-db -- psql -U postgres -d kb -c '\d+ chunks' -c 'select policyname, roles, cmd, qual from pg_policies'
----
+
What you should see: under *Policies*, `POLICY "chunks_by_group" FOR SELECT TO kb_app USING (audience && string_to_array(... current_setting('kb.groups') ...))`. The knowledge-base server logs in as `kb_app`, which is neither the table owner nor a superuser, and sets the caller's groups for each search, per transaction. Without them, `kb_app` sees no rows at all:
+
[source,bash,role=execute]
----
oc exec -n parasol-secured deploy/knowledge-base-db -- psql -U postgres -d kb -c 'set role kb_app' -c 'select classification, count(*) from chunks group by 1'
----
+
What you should see: `(0 rows)`. Even a bug in the server's own filter could not return a restricted row to an adjuster.
+
// SCREENSHOT: s3-terminal-rls.png — Terminal: \d+ chunks showing the chunks_by_group policy, and the kb_app query returning 0 rows (Showroom terminal)

. Defence in depth on the answer itself: select the *OpenShift Console* tab, project `parasol-secured`, *ConfigMaps*, `guardrails-rules`, key `output.json`.
+
What you should see: the rule `confidential-marker`: if an answer to anyone outside `claims-managers` contains "CONFIDENTIAL — Claims managers only" (any dash, any case), the guardrails proxy withholds the answer (`action=block`, detector `confidential-marker`), logged with user and agent and counted in the *Guardrails* row. It does not fire in this scenario, because the knowledge base never returned the document to rebecca or nina.contractor; it is there for the day a document is misclassified.

== Reset after this scenario

Nothing to reset: the scenario only reads. `scripts/reset.sh` does not touch the knowledge base; an administrator can reload it at any time with `scripts/knowledge-base-ingest.sh`.
