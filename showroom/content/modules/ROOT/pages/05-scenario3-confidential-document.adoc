= 05. Showcase 3: The confidential document
:navtitle: 05. Showcase 3: The confidential document
:toc: macro
:toclevels: 2

toc::[]

Parasol gives its assistant a knowledge base. Some documents are for everyone, some for claims staff, and some for claims managers only: HR material, including a restructuring plan that names an adjuster team. An adjuster has heard rumours and asks the assistant about the 2026 restructuring plan for adjuster roles. Unsecured, the assistant finds the restricted plan and tells her. Secured, retrieval runs *as her*: the restricted documents are never searched for her, so they never reach the model, and telling the assistant she is a manager changes nothing.

[NOTE]
.Know: identity on the data, not only on the tools
====
An agent with retrieval reads whatever its search returns. If the search runs with the agent's own rights, every user gets the union of everything the agent can read. On the platform, the search runs on behalf of the person: the filter comes from their token (their Keycloak groups), not from what they type, and the database enforces the same rule underneath the application.
====

== The business case

[cols="1,4"]
|===
|Who
|Rebecca Torres (claims adjuster), marcus (claims manager) and nina.contractor (night-shift contractor).

|What is at stake
|Confidential HR information (a restructuring plan that names Rebecca's own team) and other adjusters' customers. A leak means employee-relations and legal exposure and a breach of need-to-know. Once an assistant can read a document, anyone who can chat with it can ask.

|Without the platform
|The assistant searches with its own rights. Rebecca reads the manager-only plan about her team, and a colleague's customer record.

|With the platform
|Retrieval and record reads run as the person. Restricted passages never reach the model, claiming to be a manager changes nothing, and managers still get what they need.
|===

All documents are fictional. The knowledge base holds eleven of them:

[cols="1,2,3",options="header"]
|===
|Classification |Who may read it |Documents

|public
|everyone, contractors included
|How to file a claim; Motor policy FAQ; Customer service standards; Claims line opening hours

|internal
|adjusters and claims managers
|Claims handling guideline; Repair-vendor rate card 2026; Claims escalation process; Fraud referral checklist

|restricted
|claims managers only
|2026 claims operations restructuring plan; Claims staff bonus and performance-review guide 2026; Compensation adjustments 2026. Each starts with "CONFIDENTIAL — Claims managers only".
|===

== Before you start

This showcase runs on its own, in any order with the others. It only reads, so it changes no data.

* Personas: `rebecca` (claims adjuster, group `adjusters`), `marcus` (claims manager, group `claims-managers`) and `nina.contractor` (night-shift contractor, group `contractors`); passwords equal the user names.
* The knowledge base is loaded in both environments by the installation. Check it in the *Terminal* tab (read-only):
+
[source,bash,role=execute]
----
for ns in parasol-free parasol-secured; do echo -n "$ns: "; oc exec -n $ns deploy/knowledge-base-db -- psql -U postgres -d kb -Atc 'select count(*) from chunks'; done
----
+
What you should see: `parasol-free: 18` and `parasol-secured: 18`. If a count is missing or 0, an administrator reloads it from a workstation with `scripts/knowledge-base-ingest.sh` (idempotent; the Terminal identity may not create Jobs).
* `nina.contractor` works one claim, *CLM-1031*, so she has a claim page and the assistant in the portal. She needs token budget left: if you ran Showcase 4 just before, run `scripts/reset.sh` first.
* For the last part, *Records, not just documents*: claim *CLM-1029* (Amara Okafor, home, UnderReview, 19,250) is assigned to the adjuster Angela Davis, not to rebecca; CLM-1001, CLM-1004 and the other claims the earlier showcases use are assigned to Rebecca Torres. Nothing to prepare.

== Records, not just documents

The same rule holds for the claims themselves. An adjuster works the claims assigned to her; a claims manager sees every claim. Unsecured, the assistant reads any claim for anyone who asks. Secured, claims-db decides from the person in the agent's on-behalf-of token, so the assistant can only read rebecca's own claims for her.

. *Unsecured.* In the *Portal unsecured* tab as `rebecca`, open *CLM-1001* and send:
+
[source,text]
----
Show me claim CLM-1029 and its history.
----
+
What you should see: chips `called get_claim(claimNumber=CLM-1029)` and `called get_claim_history(claimNumber=CLM-1029)`, and the record: Amara Okafor, home, UnderReview, 19,250, adjuster Angela Davis (its history has no events yet). Rebecca just read a colleague's customer.

. *Secured.* In the *Portal secured* tab as `rebecca`, open *CLM-1001* and send the same message.
+
What you should see: the same chips, and an answer that she has no access to CLM-1029 because adjusters can only read the claims assigned to them (the tool returned "Access denied: Rebecca Torres (rebecca) may not read claim CLM-1029. Adjusters can read only the claims assigned to them; a claims manager can read every claim."). No claimant, amount or adjuster reaches the model. Her own claims still answer normally: try `What is the status of CLM-1004?`.
+
image::s3-secured-record-denied.png["Portal secured as rebecca: 'Show me claim CLM-1029 and its history.' answered with the access-denied message, get_claim chip visible"]

. *The screens too.* Still as `rebecca` in the *Portal secured* tab, select *Claims*.
+
What you should see: only the claims assigned to Rebecca Torres; CLM-1029 is not in her list, and her *Dashboard* counts only her caseload. Now open the claim page directly: replace the end of the address with `/ClaimDetail/CLM-1029`.
+
What you should see: a page *CLM-1029 is not assigned to you* with claims-db's refusal and no claimant, amount, documents or timeline. The screens ask claims-db with the same on-behalf-of identity the assistant's tools use, so the one rule decides both. In the *Portal unsecured* tab the same address shows the whole claim.
+
image::s3-secured-ui-not-assigned.png["Portal secured as rebecca at /ClaimDetail/CLM-1029: the 'CLM-1029 is not assigned to you' page with the access-denied text, no claim data"]

. Log out, log in as `marcus` and send the same message, then open `/ClaimDetail/CLM-1029`.
+
What you should see: the full record, in the chat and on the claim page, and CLM-1029 in his claim list. Marcus is a claims manager; the rule is the person's, not the assistant's.

. *On the platform.* Click the `trace <id>` link under rebecca's refused answer.
+
What you should see: in *MLflow*, the agent's span `tool.get_claim` (`enduser.id` `rebecca`, `gen_ai.agent.name` `parasol-claims-agent`) and with it claims-db's own span `claims-db.get_claim`: `claims.access` `denied`, `claims.claim_number` `CLM-1029`, `claims.access_reason` `assigned to Angela Davis`, `enduser.id` `rebecca`, status ERROR (the same for `claims-db.get_claim_history`). Then the audit line, in the *Terminal* tab:
+
[source,bash,role=execute]
----
oc logs -n parasol-secured deploy/claims-db --since=1h | grep 'CLAIMS ACL denied' | tail -6
----
+
What you should see: `CLAIMS ACL denied tool=get_claim claim=CLM-1029 user=rebecca via parasol-claims-agent reason=assigned to Angela Davis`, one line per refused tool call, and for the claim page `tool=ui.get_claim` (and `ui.get_claim_documents`, `ui.get_claim_history`) with the same user, agent and reason. On the dashboard (*Parasol Assistant Token Spend*, row *Gateway decisions*), *Gateway rejections by reason* has `denied, claim not assigned to the user (claims-db record access)` for `rebecca` via `parasol-claims-agent`.
+
image::s3-mlflow-record-denied.png["MLflow trace of rebecca's CLM-1029 turn: span claims-db.get_claim selected with claims.access denied, claims.claim_number CLM-1029, enduser.id rebecca"]
image::s3-dashboard-record-denied.png["Console, Parasol Assistant Token Spend, row 'Gateway decisions': the rejections table with 'denied, claim not assigned to the user (claims-db record access)' for rebecca"]
+
How it decides: claims-db verifies the token the gateway forwards (Keycloak's signature, issuer, expiry, audience `parasol-secured/claims-db`) and compares the token's `name` with the claim's adjuster, or finds `claims-managers` in its `groups`. Free runs the same server with the check off (`CLAIMS_ACL_ENFORCE` is set only in `parasol-secured`). The portal's own claim pages are not a way around it: the portal reads claims-db's REST API with the same exchanged token, and claims-db applies the same check there (tool names `ui.*` in the log, the metric and the span).

== Evidence demo

Five short steps, one command or one screen each: the same search for four people, the rule, where it is enforced, the access records, and the trace. The commands run in the *Terminal* tab and only read. The full walk through every screen is in <<Evidence details>> below.

. *One search, four answers.* The question rebecca asked, sent to the knowledge base as four identities:
+
[source,bash,role=execute]
----
scripts/evidence.sh search
----
+
What you should see:
+
[source,text]
----
unsecured portal (no check)     gets: RST-01 (restricted), RST-02 (restricted), RST-03 (restricted)  withheld: -
rebecca via the agent           gets: INT-01 (internal), ...                                          withheld: 4 restricted
marcus via the agent            gets: RST-01 (restricted), RST-02 (restricted), RST-03 (restricted)  withheld: -
nina.contractor via the agent   gets: PUB-01 (public), ...                                            withheld: 4 restricted
----
+
(The exact documents and counts follow the search wording.) Say: unsecured, the search runs with the assistant's own rights, so anyone gets the manager-only plan. Secured, it runs as the person: rebecca gets internal documents, marcus the restricted plan, the contractor only public ones. Withheld passages are counted, never returned, so they never reach the model.

. *The rule.* Which group may read which classification, and the groups each person carries:
+
[source,bash,role=execute]
----
scripts/evidence.sh kb-rule
----
+
What you should see: `restricted ... readable by: claims-managers`, `internal ... adjusters, claims-managers`, `public ... adjusters, claims-managers, contractors, developers`; then `rebecca adjusters`, `marcus claims-managers`, `nina.contractor contractors`, read from the token the agent presents on their behalf.
+
Say: every passage carries its audience; every token carries the person's groups from Keycloak. A claim in the chat ("I'm a claims manager") changes neither.

. *Enforced in the database, and for claim records too.*
+
[source,bash,role=execute]
----
scripts/evidence.sh rls
----
+
What you should see: the row-level security policy `chunks_by_group for SELECT to kb_app` (a passage is visible only if its audience overlaps the caller's groups), `rows visible: 0` for the server's own database user without a person's groups, and `get_claim CLM-1029` through the gateway: `Access denied: Rebecca Torres (rebecca) may not read claim CLM-1029 ...` for rebecca, the full record for marcus.
+
Say: the last line of defence is PostgreSQL itself: even a bug in the server could not hand a restricted passage to an adjuster. And the same rule, the person's rights and not the assistant's, governs the claim records.

. *The access records.*
+
[source,bash,role=execute]
----
scripts/evidence.sh kb-audit
----
+
What you should see: `RAG withheld doc=RST-01 classification=restricted ... from rebecca via parasol-claims-agent`, `RAG restricted doc=RST-01 accessed by marcus via parasol-claims-agent`, `RAG withheld ... from nina.contractor via parasol-claims-agent` (the searches of step 1 are on record too, like any other), and the claim refusals `tool=get_claim claim=CLM-1029 user=rebecca via parasol-claims-agent reason=assigned to Angela Davis`.
+
Say: who was refused and who read the restricted plan, by name and agent, without anyone having to ask the model what it saw.

+
What you should see: *Passages withheld by classification, user and agent* with `restricted` for `rebecca` and `internal` for `nina.contractor`; *Restricted documents read* with `RST-01` for `marcus`, all via `parasol-claims-agent`.

image::s3-dashboard-knowledge-base.png["Console, Parasol Assistant Token Spend, row 'Knowledge base': searches per user, withheld restricted for rebecca and internal for nina.contractor, restricted documents read by marcus"]

Then, in the *Portal secured* tab as rebecca, click the `trace <id>` link under her first answer.

. Where the groups come from: in the Keycloak admin *private window* (page 02), realm `parasol`, *Groups*.
+
What you should see: `adjusters` (rebecca), `claims-managers` (marcus), `contractors` (nina.contractor). Open `contractors`, *Role mapping*: `tool:search_knowledge` on `parasol-secured/knowledge-base`, the same role the other groups hold. Everyone may *call* the search; what each person gets back is decided by the groups in the token the agent presents on their behalf (*Clients*, `parasol-claims-agent`, *Client scopes*: `groups` is a default scope, and `tool:search_knowledge` is inside the agent's ceiling).
+
image::s3-keycloak-groups.png["Keycloak admin, realm parasol, Groups > contractors > Role mapping: tool:search_knowledge on parasol-secured/knowledge-base"]

. The last line of defence is the database. In the *Terminal* tab (read-only):
+
[source,bash,role=execute]
----
oc exec -n parasol-secured deploy/knowledge-base-db -- psql -U postgres -d kb -c '\d+ chunks' -c 'select policyname, roles, cmd, qual from pg_policies'
----
+
What you should see: under *Policies*, `POLICY "chunks_by_group" FOR SELECT TO kb_app USING (audience && string_to_array(... current_setting('kb.groups') ...))`. The knowledge-base server logs in as `kb_app`, which is neither the table owner nor a superuser, and sets the caller's groups for each search, per transaction. Without them, `kb_app` sees no rows at all:
+
[source,bash,role=execute]
----
oc exec -n parasol-secured deploy/knowledge-base-db -- psql -U postgres -d kb -c 'set role kb_app' -c 'select classification, count(*) from chunks group by 1'
----
+
What you should see: `(0 rows)`. Even a bug in the server's own filter could not return a restricted row to an adjuster.
+
image::s3-terminal-rls.png["Terminal: \d+ chunks showing the chunks_by_group policy, and the kb_app query returning 0 rows"]

. Defence in depth on the answer itself: select the *OpenShift Console* tab, project `parasol-secured`, *ConfigMaps*, `nemo-parasol-chat`: the output rail `parasol confidential marker` in `config.yaml`, its rule in `actions.py`.
+
What you should see: if an answer to anyone outside `claims-managers` contains "CONFIDENTIAL — Claims managers only" (any dash, any case), NeMo Guardrails blocks it and the guardrails proxy withholds the answer (`action=block`, detector `confidential-marker`), logged with user and agent and counted in the *Guardrails* row. It does not fire in this showcase, because the knowledge base never returned the document to rebecca or nina.contractor; it is there for the day a document is misclassified.
