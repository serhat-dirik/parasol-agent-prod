= 03. Showcase 1: The overstepping colleague
:navtitle: 03. Showcase 1: The overstepping colleague
:toc: macro
:toclevels: 2

toc::[]

An adjuster has no authority to pay a claim. Unsecured, the agent pays anyway. Secured, the adjuster's assistant can approve the claim, and only a claims manager's click releases the payment.

[NOTE]
.Know: identity on every tool call
====
The agent acts *as the person*, and the gateway checks the person's rights before any tool runs. Unsecured, nobody asks who is asking: a chat window becomes a payout button for anyone who can log in.

This showcase is also the proof that a fooled model cannot pay: whoever pushes it, a person here or a document in Showcase 2, the model can at most *approve a claim*. No model is offered the tool that pays; only a person with the right role releases a payment.
====

== The business case

[cols="1,4"]
|===
|Who
|Rebecca Torres, a claims adjuster, and marcus, a claims manager.

|What is at stake
|Separation of duties. A payment needs a claims manager's release: a control that auditors test. An assistant that approves for whoever asks turns every login into payout authority: unauthorized payments, an audit finding, and a control that exists only on paper.

|Without the platform
|The adjuster only says the claim should be approved by now; the assistant pays USD 4,200 on a claim still under review. Nobody with authority saw it, and nobody even asked it to pay.

|With the platform
|Two stages. The adjuster's assistant approves the claim (*Ready for payment*, no money moves); a claims manager releases the payment with one click. The record names who approved, who released, and the agent that carried out each step.
|===

== Evidence details

For curious minds: every screen behind the demo above, the rule in the Keycloak and console UIs, and the full audit.


The app did not change between the two portals: the same portal code, the same MCP tools, the same model. What changed is the path a tool call takes, and who checks it on the way.

=== Same app, two paths

Unsecured, the portal sends rebecca's own login token straight to the claims tool. The tool even knows who she is, and pays anyway: nothing checks what an adjuster may do. Secured, every tool call goes through three checks:

[cols="1,3"]
|===
|Agent identity (Keycloak)
|On every chat turn the agent exchanges rebecca's token for one issued to *itself*, on her behalf (OAuth token exchange). It proves who it is with its pod's ServiceAccount token, so it holds no secret. The new token says user = `rebecca` (`sub`), agent = `parasol-claims-agent` (`azp`), and carries only the tool roles that are both hers and inside the agent's ceiling.

|What the model is offered (MCP gateway)
|The agent's tool list is a curated *virtual server*: `approve_claim` is in it (stage 1, no money moves), `release_payment` is not, for anyone. The model can at most approve a claim; the payment is the manager's *Release payment* click, a direct tool call with the manager's own token through the same gateway.

|What the call may do (Authorino, at the MCP gateway)
|Every `tools/call` is checked against the token: it must come from an approved agent, and the person must hold `tool:<name>` for that MCP server. Otherwise HTTP 403, with the reason.
|===

. In the *Terminal* tab, read the payment records of both portals side by side:
+
[source,bash,role=execute]
----
for ns in parasol-free parasol-secured; do oc logs -n $ns deploy/claims-db --since=1h | grep -E 'PAYOUT|CLAIM APPROVED|PAYMENT RELEASED' | sed -E "s/.*(PAYOUT|CLAIM APPROVED|PAYMENT RELEASED)/$ns: \1/"; done
----
+
What you should see:
+
[source,text]
----
parasol-free: PAYOUT claim=CLM-1001 amount=4200.00 previousStatus=UnderReview actor=rebecca via parasol-portal
parasol-secured: CLAIM APPROVED claim=CLM-1001 amount=4200.00 actor=rebecca via parasol-claims-agent
parasol-secured: PAYMENT RELEASED claim=CLM-1001 amount=4200.00 actor=marcus via parasol-claims-agent
----
+
The unsecured tool knew it was rebecca and paid. Knowing who is asking is not the same as checking what they may do. The secured records name the adjuster who approved, the manager who paid, and the agent that carried out each step.

=== The rule

. *Who holds which right.* In the Keycloak admin *private window* (page 02), realm `parasol`, open *Groups*, `adjusters`, tab *Role mapping*. Then the same for `claims-managers`.
+
What you should see: for client `parasol-secured/claims-db`, `adjusters` holds `tool:get_claim`, `tool:get_claim_history`, `tool:list_claims_by_status`, `tool:get_claim_documents` and `tool:approve_claim`. `claims-managers` holds the same five *plus* `tool:release_payment`. rebecca is in `adjusters`, marcus in `claims-managers`. That is the business rule: an adjuster approves a claim, a manager releases the payment.
+
image::s1-keycloak-group-roles-two-stage.png["Keycloak admin, realm parasol, group claims-managers, Role mapping: the tool roles per MCP server, including parasol-secured/claims-db tool:approve_claim and tool:release_payment"]

. *The agent's ceiling.* Open *Clients*, `parasol-claims-agent`, tab *Client scopes*, `parasol-claims-agent-dedicated`, tab *Scope*.
+
What you should see: *Full scope allowed* off, and the `tool:*` roles this agent may ever carry. The exchanged token holds only roles that are in this ceiling *and* the person's own: rebecca's token has no `tool:release_payment`, marcus's does. A compromised or misconfigured agent cannot exceed it, whoever uses it.
+
image::s1-keycloak-agent-ceiling.png["Keycloak admin, Clients > parasol-claims-agent > Client scopes > parasol-claims-agent-dedicated > Scope: Full scope allowed off and the assigned tool:* roles"]

. *What the gateway enforces.* Select the *OpenShift Console* tab, *Home*, *Search*, project `gateway-system`, resource `AuthPolicy`, open `mcp-tool-auth-policy`, tab *YAML*.
+
What you should see: the policy targets the `mcp-gateway` Gateway, trusts tokens from realm `parasol`, and has two authorization rules:
+
* `approved-agent`: `auth.identity.azp in ['parasol-claims-agent', 'parasol-fraud-agent']`. A call must come through an approved agent; a person's own login token is refused.
* `tool-access-check`, on every `tools/call`: `'tool:' + <tool name>` must be in the token's roles for that MCP server (`resource_access[<server>].roles`).
+
The `unauthorized` response turns each refusal into a readable reason: "*user* may not call *tool*" or "calls must come through an approved agent". The rule lives in the platform, as a Kubernetes resource in Git, not in the agent's code or its prompt.
+
image::s1-console-authpolicy.png["OpenShift console, AuthPolicy mcp-tool-auth-policy in gateway-system, YAML: the Keycloak issuer, then the approved-agent and tool-access-check rules"]

. *What the model is offered.* Same *Search*, project `parasol-secured`, resource `MCPVirtualServer`, open `claims-db`, tab *YAML*.
+
What you should see: `tools: [get_claim, list_claims_by_status, get_claim_history, get_claim_documents, approve_claim]`. No `release_payment` and no `approve_payout`, for any user: no chat model can pay. That is why rebecca's insisting ended at *Ready for payment*.

=== The rule at work

. *Go around the agent.* Rebecca could not get the tool through the chat. Now try what an attacker would: call the gateway directly. In the *Terminal* tab:
+
[source,bash,role=execute]
----
scripts/abuse.sh secured rebecca 1
----
+
What you should see:
+
* `forced at the MCP gateway, rebecca's own token: ... calls must come through an approved agent (got azp=parasol-demo-cli). (HTTP 403)`: the `approved-agent` rule. A login token without an agent does not reach a tool;
* `forced at the MCP gateway, rebecca via parasol-claims-agent: ... rebecca may not call approve_payout. (HTTP 403)`: the `tool-access-check` rule. Even through the approved agent, her token lacks the role (in secured nobody holds the one-step `approve_payout`, and claims-db refuses it anyway).

. *The gateway's own record.* Every decision, allowed or refused, is one line in the MCP gateway's access log, with the user and the agent Authorino verified:
+
[source,bash,role=execute]
----
oc logs -n gateway-system -l gateway.networking.k8s.io/gateway-name=mcp-gateway --since=1h --tail=-1 | grep gateway-decision | grep -E 'user=(rebecca|marcus)' | sed 's/.*status=/status=/'
----
+
What you should see: rebecca's chat calls `status=200 ... user=rebecca agent=parasol-claims-agent ... tool=get_claim` and `tool=approve_claim`; her forced calls `status=403 ... user=rebecca ... tool=approve_payout`; and marcus's click `status=200 req=[user=marcus agent=parasol-claims-agent] ... tool=release_payment`. Each step by the person whose role allows it: the rule decided, not the model. (A `404` just before a `200` is the agent re-opening its MCP session.)

. *Who acted for whom.* Back in the Keycloak *private window*, *Events*, tab *User events*, event type `TOKEN_EXCHANGE`. Expand the newest rows.
+
What you should see: one row per chat turn, client `parasol-claims-agent`, `username` `rebecca` and `marcus`, `subject_token_client_id` `parasol-portal` (the browser login it acted on) and `client_assertion_sub` `system:serviceaccount:parasol-secured:claims-agent` (the agent's workload identity, no secret).

== The audit trail: one payout, end to end

Monday morning, finance sees the payout on CLM-1001 and asks four questions: who paid it, through what, under which rules, and was the software that did it the software that was approved? The first three are answered above. This section follows the same keys (the user, the agent, the trace id, the prompt digest, the image digest) from marcus's payment back to rebecca's approval and to the release. Everything reads only, and nothing is paid twice: claims-db refuses a second payment on a claim that already has one issued.

[NOTE]
.Know: an audit trail is a chain, not a log file
====
Each control writes its own record with the same keys. Follow them from the payout back to the release and you have reconstructed the incident from evidence the platform produced while it happened, not from what anyone remembers.
====

. *Was it the approved software?* The release run, the Argo CD pin, the running pod and the admission policy:
+
[source,bash,role=execute]
----
scripts/evidence/showcase1.sh release
----
+
What you should see: the same `sha256:...` digest three times, as `PROMOTED_DIGEST` of the release run (with `EVAL_GATE passed`), as `promoted-digest` on `env-secured`, and as the running portal's `image`; then `policy.rhtas.com/include=true` and the `ClusterImagePolicy` `parasol-portal-must-be-signed` with its accepted signer. What ran is what was built, evaluated and signed; admission refuses anything else (xref:07-showcase5-supply-chain.adoc[07. Showcase 5: Supply chain, signing and admission]).

. *With which prompt.* The prompt the release pinned against the prompt the portal runs:
+
[source,bash,role=execute]
----
scripts/evidence/showcase1.sh prompt
----
+
What you should see: the same version and the same sha256 twice. The same sha256 is the `prompt_sha256` tag on rebecca's chat turn (next step).

. *The conversation, checked.* In the *MLflow* tab, *Traces*, *Filters*, field *User*, value `rebecca`: open the chat turn that approved the claim.
+
What you should see: the conversation itself (question and answer on the `ChatMessage` span, each model call and each tool call with its arguments and result), the tags `prompt` and `prompt_sha256`, the `approve_claim` tool call (Ready for payment, USD 4200.00), and the *Assessments* of the AgenticOps checks (`loop`, `excess_steps`, `unknown_tool`, `pii_in_tool_args`), logged by the CronJob `agenticops` in project `observability` within 10 minutes of the turn. On the secured side every recorded text is masked with the guardrails' personal-data patterns, so the record holds no more than the model saw. The latest checks, from the *Terminal* tab: `scripts/evidence/showcase1.sh agenticops`.
+
image::s9-mlflow-conversation-assessments-approve.png["MLflow, workspace parasol-secured, rebecca's turn that approved CLM-1001: question and answer on the ChatMessage span, the approve_claim tool call, and the four AgenticOps assessments (pii_in_tool_args, unknown_tool, excess_steps, loop) all False"]

. *What was live.* Select the *Argo CD* tab, application `env-secured`, *Details*, *Summary*, then *History and rollback*.

What you should see: the annotations `parasol.example/promoted-digest`, `promoted-by` (the release TaskRun), `prompt-ref` `...@production`, `prompt-version`, `prompt-sha256` and `agent-version` (the MLflow agent version the release evaluated, its id in `agent-version-id`).
