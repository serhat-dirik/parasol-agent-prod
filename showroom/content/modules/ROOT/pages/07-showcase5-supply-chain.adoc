= 07. Showcase 5: Supply chain, signing and admission
:navtitle: 07. Showcase 5: Supply chain, signing and admission
:toc: macro
:toclevels: 2

toc::[]

The agent reached production the way any workload should: a pipeline that evaluates, signs and verifies what it builds, and an admission policy that refuses anything unsigned. What runs in `parasol-secured` is provably the image the pipeline built.

[NOTE]
.Know: provenance is enforced at the door
====
What runs next to customer data must be the exact image the pipeline built, evaluated and signed. An unsigned or tampered image cannot start in the secured namespace, whoever deploys it.
====

== Why it matters

What runs next to customer data must be exactly what was built, scanned, evaluated and approved. A tampered or unsigned image, or a workload calling an unapproved model, bypasses every other control. Without the platform any image can run, and any workload can call any model endpoint it has a key for. Here the pipeline signs and verifies every release, admission refuses unsigned images in the secured namespace, and only approved models are reachable.

How a release reaches production. Build, scan and SBOM, the evaluation gate, two signatures and Conforma run in one pipeline; only a release that passed is promoted, and admission checks the signature again when Argo CD rolls it out:

image::s5-release-flow.png["The release pipeline: Git, build, then scan and SBOM, the evaluation gate (with an MLflow agent version) and two signatures verified by Conforma; promote pins the digest and prompt on Argo CD env-secured; Argo CD syncs; admission checks the signature; the portal runs the exact digest. A failed gate skips promote; an unsigned image is refused at admission"]

== Run it

Five short steps, one command or one screen each: what runs, the rule, how the platform enforces it, and the record it leaves. Everything reads only, except step 3, which starts and removes two test pods in a demo namespace. The full walk through every screen is in <<Look closer>> below.

. *What runs in production.* The release run, the Argo CD pin, the running pod and the admission policy:
+
[source,bash,role=execute]
----
scripts/evidence/showcase5.sh release
----
+
What you should see: one `sha256:...` digest three times: `PROMOTED_DIGEST` of the release run (next to `EVAL_GATE passed` and `SIGNED_IMAGES` / `KEYLESS_SIGNED_IMAGES` listing `parasol-portal`), `promoted-digest` on `env-secured`, and the running portal's `image`.
+
Say: the image that runs next to customer data is the one the pipeline built, evaluated and signed. Nothing else has a path to production.

. *The rule.* The last lines of the same output: namespace `parasol-secured` with `policy.rhtas.com/include=true`, and the `ClusterImagePolicy` `parasol-portal-must-be-signed` for the portal images with two accepted signers, `keyless-tas` (Trusted Artifact Signer) and `cluster-cosign-key`.
+
Say: the rule is a cluster resource. Admission checks the signature of every portal image before a pod starts, whoever deploys it.

. *Admission enforces it.* What the policy controller checks on every pod in `parasol-secured`:
+
image::s5-admission.png["Admission: any deploy, then namespace in scope (policy.rhtas.com/include=true), then image matches a policy (portal, vendor tools), then a valid signature: admitted, or denied; namespaces out of scope are not enforced"]
+
Try an unsigned and a signed portal image:
+
[source,bash,role=execute]
----
scripts/signing-demo.sh
----
+
What you should see: the unsigned image refused by the admission webhook, naming the missing signature; the signed one admitted. The script removes its test pods.

. *Only approved models.* The model path of each portal and what each can reach:
+
[source,bash,role=execute]
----
scripts/evidence/showcase5.sh models
----
+
What you should see: the unsecured portal calls the provider's URL directly; the secured portal calls `http://guardrails-proxy.parasol-secured.svc:8080/v1`, the guardrails proxy, which alone reaches MaaS. Then the reachability table: `parasol-free` gets `401` from the public model API and from the MaaS route (it answered, and only wants a key); `parasol-secured` gets `000` for both (the connection never left the namespace).
+
Say: no key would help the secured portal call a model around the platform. Its only model path is the guardrails proxy, then MaaS, which routes only registered models.

. *Watch it.* Select the *OpenShift Console* tab, *Pipelines*, project `parasol-build`, run `parasol-portal-release-production`.
+
What you should see: build, scan, the two signatures, Conforma, the evaluation gate, then `promote`. The run's *Details* tab lists the same `PROMOTED_DIGEST` as step 1.

== Look closer

For curious minds: every screen behind the demo above.

=== The secure build pipeline

. Select the *Argo CD* tab and open application `platform-pipeline`.
+
What you should see: the app is Synced and Healthy. The demo's repository is read-only, so this Argo CD application is what creates the `parasol-portal-secure-build` Pipeline, its Tasks and the promote permissions in `parasol-build` and keeps them as Git describes: a change made in the cluster, such as removing the evaluation step, is put back. Pipeline runs are not part of the app. In a product setup these definitions usually live in the application's own repository and run through Pipelines as Code on each push.

. Select the *OpenShift Console* tab, open *Pipelines*, project `parasol-build`, *Pipeline runs*, then `parasol-portal-release-production`.
+
What you should see: the portal built from source (`build-container`); then in parallel the vulnerability scan (`scan-image`), two signatures (`sign-images` with the cluster key and `keyless-sign` through Trusted Artifact Signer) and the Showcase 6 gate (`agent-eval`); `verify-enterprise-contract` (Conforma) checks the signatures and provenance; only then `promote`, next to `generate-sbom`; `register-agent-version` records the evaluated agent configuration as an MLflow agent version before `promote` runs. The red marker on `promote` is a console display issue for completed runs; the run status *Succeeded* and the `promote` log are the record.
+
image::sc-pipeline-v1-promoted.png["The release run: clone and build; scan-image, sign-images, keyless-sign and agent-eval in parallel; verify-enterprise-contract and register-agent-version; generate-sbom and promote; finally show-summary and show-sbom"]

. Open the `keyless-sign` task log.
+
What you should see: `tlog entry created` and `VERIFIED (keyless)` for the portal digest. No long-lived key: the pipeline's workload identity gets a certificate valid for minutes, signs, and the signature lands in the Rekor transparency log. `sign-images` shows the same image signed with the cluster key; admission accepts either.

. Open the `promote` task log.
+
What you should see: first `Prompt pinned: agent-prompt-release = parasol-claims-assistant-system-prompt/1 (parasol-claims-assistant-system-prompt@production, sha256 ...)`, then `PROMOTED: env-secured runs ...parasol-portal@sha256:...` with the prompt version, its sha256 and the agent version (`parasol-claims-agent@<version>`) the gate evaluated. The release ships the prompt like the image: `agent-eval` registered `gitops/envs/secured/system-prompt.txt` as the version behind `@production` and evaluated it, and `promote` pins exactly that text in the ConfigMap `agent-prompt-release`, the only prompt the secured portal reads. A commit that edits the prompt file changes nothing at run time until the next release has gated and pinned it. Promotion writes nothing to Git: the repository stays read-only for releases. The task pins the signed digest on the Argo CD Application `env-secured` and waits until Argo CD reports it Synced and Healthy.

. Select the *Argo CD* tab, open application `env-secured`, click *Details* and select the *Parameters* tab.
+
What you should see: under *Images*, the `parasol-portal` override with the promoted digest. The *Summary* tab carries the audit trail as annotations: `parasol.example/promoted-digest`, `promoted-by` (the TaskRun), `prompt-ref`, `prompt-version` (the registry version pinned), `prompt-sha256` (the digest of the pinned prompt text) and `agent-version` (the MLflow agent version the gate evaluated). *History and rollback* lists the sync that rolled it out. The `prompt-version` here (`parasol-claims-assistant-system-prompt/1`, the version behind `@production`) is the same value every live chat trace carries as its `prompt` tag, and `prompt-sha256` matches the trace's `prompt_sha256` (xref:08-showcase6-eval-gate.adoc[08. Showcase 6: The evaluation gate]): release record and runtime evidence agree.
+
image::sc-argo-env-secured-promote.png["Argo CD, application env-secured, Summary: the annotations parasol.example/agent-version, model-only-baseline, promoted-by, promoted-digest, prompt-ref, prompt-sha256 and prompt-version written by the promote step; Synced, Healthy"]

. Close the panel and open the `portal` Deployment.
+
What you should see: the secured portal runs exactly that pinned digest; admission verified its signature when Argo CD rolled it out.

=== Admission refuses an unsigned image

The `ClusterImagePolicy` `parasol-portal-must-be-signed` admits only portal images signed by the pipeline.

. In the *OpenShift Console* tab, open the policy. Direct link: link:{console_url}/k8s/cluster/policy.sigstore.dev~v1beta1~ClusterImagePolicy/parasol-portal-must-be-signed/yaml[ClusterImagePolicy parasol-portal-must-be-signed,window=_blank].
+
What you should see: the image pattern for the portal and the two accepted signing authorities (keyless and the cluster key).

. In the *Terminal* tab, try to run an unsigned and a signed portal image in the admission demo namespace:
+
[source,bash,role=execute]
----
scripts/signing-demo.sh
----
+
What you should see:
+
* the *unsigned* image is refused by the admission webhook, with a message naming the missing signature;
* the *signed* image is admitted and its pod is created;
* the script removes its test pods at the end.
+
Signatures, the admission decision and the promote history on `env-secured` together answer "what runs in production, and who let it in".
+
image::sc-admission-refused.png["Terminal: scripts/signing-demo.sh, the unsigned portal image denied by the admission webhook (policy parasol-portal-must-be-signed, no keyless or key signature), the signed image the release promoted admitted, then cleanup"]

=== Only approved models

Shadow AI: a developer is in a hurry, has a personal key for a public model API, and points a workload at it directly, around the platform's guardrails and budgets. Same model swap, different blast radius. On the secured side the image can be signed and the prompt gated, and still the question is: which models can this workload reach at all?

. *Unsecured.* In the *Terminal* tab, from the unsecured portal pod, call a public model API without a key:
+
[source,bash,role=execute]
----
oc exec -n parasol-free deploy/portal -- curl -sS -o /dev/null -w '%{http_code}\n' --max-time 8 https://api.openai.com/v1/models
----
+
What you should see: `401`. The endpoint answered and only wants a key: with the developer's own key in an environment variable, this workload would talk to an unapproved model, outside every budget, guardrail and trace. The unsecured namespace also holds the upstream provider key itself (Secret `maas-credentials`).

. *Secured.* The same call from the secured portal pod:
+
[source,bash,role=execute]
----
oc exec -n parasol-secured deploy/portal -- curl -sS -o /dev/null -w '%{http_code}\n' --max-time 8 https://api.openai.com/v1/models
----
+
What you should see: `000` and `curl: (28) Failed to connect to api.openai.com port 443: Connection timed out`. No key would help: the packet never leaves the namespace.

. *Why.* Select the *OpenShift Console* tab, project `parasol-secured`, *Networking*, *NetworkPolicies*.
+
What you should see: `default-deny` (every pod, ingress and egress), then one allow-list per workload: `portal` and `parasol-agent` reach only the MCP gateway and Keycloak (by their in-cluster Services, not through the router), the guardrails proxy (pods `component: guardrails-proxy`, port 8080, their only model path) and the OTel collector; `guardrails` (the guardrails proxy) reaches only pods in its own namespace (NeMo Guardrails, the detectors), the in-cluster MaaS gateway and OTel; `parasol-nemo` takes calls only from the MCP gateway and the guardrails proxy; the MCP servers reach only OTel (and Keycloak's signing keys). There is no rule to the internet.
+
image::sc-networkpolicies-secured.png["Console, project parasol-secured, NetworkPolicy portal: egress only to the MCP gateway, Keycloak, the guardrails-proxy pods on port 8080, OTel and claims-db"]
+

. *The drop is on record.* The namespace carries `k8s.ovn.org/acl-logging: {"deny": "alert"}`, so OVN logs every connection a NetworkPolicy drops on the pod's node. From a workstation as an administrator (the Terminal's identity may not read node logs):
+
[source,bash]
----
node=$(oc get pod -n parasol-secured -l app=portal -o jsonpath='{.items[0].spec.nodeName}')
oc adm node-logs $node --path=ovn/acl-audit-log.log | grep 'NP:parasol-secured:Egress' | tail -3
----
+
What you should see: `name="NP:parasol-secured:Egress", verdict=drop, severity=alert, ... nw_src=<the portal pod IP>, nw_dst=<the public address>, tp_dst=443`. Without the annotation, NetworkPolicy drops are not logged at all; the namespace in this demo opts in.

. *Only registered models, only MaaS keys.* Select the *OpenShift Console* tab, project `models-as-a-service`, *Home*, *Search*, resource `MaaSModelRef`: the models the platform serves (the assistant's model, the guard model and the evaluation's judge model, chosen at setup; tested with `qwen3-14b`, `granite-guardian-3-1-8b` and `gpt-oss-120b`), each *Ready* behind `maas-default-gateway` and backed by an `ExternalModel` whose upstream provider key lives in that project only. In the *OpenShift AI* tab, *Settings*, *MaaS governance* lists the subscriptions that may use each one. Then, in the *OpenShift Console* tab, project `parasol-secured`, *Secrets*: `maas-credentials` and `maas-portal-keys` hold *MaaS* keys, each bound to a subscription with its own token limit (xref:06-showcase4-night-shift.adoc[06. Showcase 4: The night shift]); no provider key is in the namespace. Every model call goes portal -> guardrails proxy -> MaaS, and MaaS routes only to the models registered in it: a request for any other model name finds no route.
+
image::sc-maas-models.png["Console, project models-as-a-service, MaaSModelRefs: gpt-oss-120b (judge), granite-guardian-3-1-8b (guard) and qwen3-14b (agent), each Ready behind maas-default-gateway"]
+

. *No path around the guardrails.* The secured portal reaches Keycloak and the MCP gateway by their in-cluster Services, so its policy has no rule to the cluster's router, and with it none to the platform's own MaaS route. In the *Terminal* tab:
+
[source,bash,role=execute]
----
oc exec -n parasol-secured deploy/portal -- curl -sS -o /dev/null -w '%{http_code}\n' --max-time 8 https://maas.apps.$(oc get dns cluster -o jsonpath='{.spec.baseDomain}')/v1/models
----
+
What you should see: `000`, `curl: (28) Connection timed out`. Even with a MaaS key the portal cannot skip the guardrails proxy: the only model path it has is portal -> guardrails proxy -> MaaS.
