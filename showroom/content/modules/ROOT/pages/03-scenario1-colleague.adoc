= 03. Showcase 1: The colleague
:navtitle: 03. Showcase 1: The colleague
:toc: macro
:toclevels: 2

toc::[]

An adjuster has no authority to approve a payout. Unsecured, the agent does it anyway. Secured, the tool is never even offered to the adjuster, and only a manager's click writes.

[NOTE]
.Know: identity on every tool call
====
The agent acts *as the person*, and the gateway checks the person's rights before any tool runs. Unsecured, nobody asks who is asking: a chat window becomes a payout button for anyone who can log in.
====

== The business case

[cols="1,4"]
|===
|Who
|Rebecca Torres, a claims adjuster, and marcus, a claims manager.

|What is at stake
|Separation of duties. A payout needs a claims manager's approval: a four-eyes control that auditors test. An assistant that approves for whoever asks turns every login into payout authority: unauthorized payments, an audit finding, and a control that exists only on paper.

|Without the platform
|The adjuster only says the claim should be approved by now; the assistant pays AED 4,200 on a claim still under review. Nobody with authority saw it, and nobody even asked it to pay.

|With the platform
|The adjuster can only propose. The manager approves with one click. The record names the person who approved and the agent that carried it out.
|===

== Evidence demo

Five short steps, one command or one screen each: what happened, the rule, how the platform enforces it, and the record it leaves. Everything runs in the *Terminal* tab and reads only; nothing is paid. The full walk through every screen is in <<Evidence details>> below.

. *Same app, two outcomes.* The payout records the claims tool wrote on each portal:
+
[source,bash,role=execute]
----
scripts/evidence.sh payouts CLM-1001
----
+
What you should see:
+
[source,text]
----
parasol-free: PAYOUT claim=CLM-1001 ... actor=rebecca via parasol-portal
parasol-secured: PAYOUT claim=CLM-1001 ... actor=marcus via parasol-claims-agent
----
+
Say: the unsecured tool knew it was rebecca, and paid anyway. Knowing who is asking is not checking what they may do. The secured record names the person who approved and the agent that carried it out.

. *The rule.* Who may do what, as Keycloak hands it to every service in the user's token:
+
[source,bash,role=execute]
----
scripts/evidence.sh roles
----
+
What you should see: rebecca, group `adjusters`, tools `get_claim, get_claim_documents, get_claim_history, list_claims_by_status`; marcus, group `claims-managers`, the same tools *plus* `approve_payout`.
+
Say: this is the whole business rule, an adjuster reads, a manager approves. It is kept in Keycloak groups (a click in its admin console), not in the agent's code or its prompt.

. *The agent acts on her behalf, never above her.* Rebecca's login token next to the token the claims agent obtains for her:
+
[source,bash,role=execute]
----
scripts/evidence.sh token rebecca
----
+
What you should see: the same `user` (`rebecca`), the same `groups` and the same `tools`, but the `client` changes from the login client to `parasol-claims-agent`.
+
Say: on every chat turn the agent exchanges her token for one issued to itself, on her behalf (OAuth token exchange). It proves who it is with its pod's ServiceAccount token, so it holds no secret. The gateway and every tool now see both names: who asked, and which agent did it. And the agent can never carry more rights than the person.

. *The gateway enforces the rule.* Live calls straight at the MCP gateway, then the gateway's own decision log:
+
[source,bash,role=execute]
----
scripts/evidence.sh gateway
----
+
What you should see:
+
[source,text]
----
rebecca, own login token           get_claim       HTTP 403  ... calls must come through an approved agent ...
rebecca via parasol-claims-agent   get_claim       HTTP 200  allowed
rebecca via parasol-claims-agent   approve_payout  HTTP 403  ... rebecca may not call approve_payout.
marcus via parasol-claims-agent    get_claim       HTTP 200  allowed
----
+
then the decision log, with marcus's Approve click from the walkthrough: `200  marcus via parasol-claims-agent  approve_payout`.
+
Say: two checks at the gateway on every tool call. The call must come through an approved agent, and the person must hold the tool's role. Even going around the agent, rebecca cannot pay; marcus's click passed the same check. The rule is applied by the platform, one place for every agent and every tool.

. *Watch it and trace it.* Select the *OpenShift Console* tab, *Observe*, *Dashboards (Perses)*, project `openshift-operators`, *Parasol Assistant Token Spend*, row *Gateway decisions*.
+
What you should see: *Gateway rejections by reason* counts `403 not via an approved agent (MCP gateway)` and `403 role does not allow the tool (MCP gateway)`; *Tool calls by tool, user, agent and status* lists `approve_payout`, `marcus`, `parasol-claims-agent`, `200`.
+
image::s1-dashboard-rejections.png["Console, Observe > Dashboards (Perses), openshift-operators, Parasol Assistant Token Spend, row 'Gateway decisions': the rejections table with both 403 reasons and the tool-calls table with approve_payout / marcus / parasol-claims-agent / 200"]
+
Then, in the *Portal secured* tab as marcus, click the `trace <id>` link under the approved card.
+
What you should see: the *MLflow* trace: user `marcus`, tags `agent` `parasol-claims-agent` and `action` `approve_payout CLM-1001`, and a `gateway.authz` span with status OK. == Evidence details

For curious minds: every screen behind the demo above, the rule in the Keycloak and console UIs, and the full audit.


The app did not change between the two portals: the same portal code, the same MCP tools, the same model. What changed is the path a tool call takes, and who checks it on the way.

=== Same app, two paths

Unsecured, the portal sends rebecca's own login token straight to the claims tool. The tool even knows who she is, and pays anyway: nothing checks what an adjuster may do. Secured, every tool call goes through three checks:

[cols="1,3"]
|===
|Agent identity (Keycloak)
|On every chat turn the agent exchanges rebecca's token for one issued to *itself*, on her behalf (OAuth token exchange). It proves who it is with its pod's ServiceAccount token, so it holds no secret. The new token says user = `rebecca` (`sub`), agent = `parasol-claims-agent` (`azp`), and carries only the tool roles that are both hers and inside the agent's ceiling.

|What the model is offered (MCP gateway)
|The agent's tool list is a curated *virtual server*: `approve_payout` is not in it for anyone. The model can only *propose*; the real write is the manager's *Approve* click, a direct tool call with the manager's own token through the same gateway.

|What the call may do (Authorino, at the MCP gateway)
|Every `tools/call` is checked against the token: it must come from an approved agent, and the person must hold `tool:<name>` for that MCP server. Otherwise HTTP 403, with the reason.
|===

. In the *Terminal* tab, read both payout records side by side:
+
[source,bash,role=execute]
----
for ns in parasol-free parasol-secured; do oc logs -n $ns deploy/claims-db --since=1h | grep PAYOUT | sed "s/.*PAYOUT/$ns: PAYOUT/"; done
----
+
What you should see:
+
[source,text]
----
parasol-free: PAYOUT claim=CLM-1001 amount=4200.00 previousStatus=UnderReview actor=rebecca via parasol-portal
parasol-secured: PAYOUT claim=CLM-1001 amount=4200.00 previousStatus=UnderReview actor=marcus via parasol-claims-agent
----
+
The unsecured tool knew it was rebecca and paid. Knowing who is asking is not the same as checking what they may do. The secured record names the person who approved and the agent that carried it out.

=== The rule

. *Who holds which right.* In the Keycloak admin *private window* (page 02), realm `parasol`, open *Groups*, `adjusters`, tab *Role mapping*. Then the same for `claims-managers`.
+
What you should see: for client `parasol-secured/claims-db`, `adjusters` holds `tool:get_claim`, `tool:get_claim_history`, `tool:list_claims_by_status` and `tool:get_claim_documents`. `claims-managers` holds the same four *plus* `tool:approve_payout`. rebecca is in `adjusters`, marcus in `claims-managers`. That is the business rule: an adjuster reads, a manager approves.
+
// SCREENSHOT: s1-keycloak-group-roles.png — Keycloak admin, realm parasol, Groups > claims-managers > Role mapping: the parasol-secured/claims-db tool roles including tool:approve_payout (adjusters next to it without it)

. *The agent's ceiling.* Open *Clients*, `parasol-claims-agent`, tab *Client scopes*, `parasol-claims-agent-dedicated`, tab *Scope*.
+
What you should see: *Full scope allowed* off, and the `tool:*` roles this agent may ever carry. The exchanged token holds only roles that are in this ceiling *and* the person's own: rebecca's token has no `tool:approve_payout`, marcus's does. A compromised or misconfigured agent cannot exceed it, whoever uses it.
+
image::s1-keycloak-agent-ceiling.png["Keycloak admin, Clients > parasol-claims-agent > Client scopes > parasol-claims-agent-dedicated > Scope: Full scope allowed off and the assigned tool:* roles"]

. *What the gateway enforces.* Select the *OpenShift Console* tab, *Home*, *Search*, project `gateway-system`, resource `AuthPolicy`, open `mcp-tool-auth-policy`, tab *YAML*.
+
What you should see: the policy targets the `mcp-gateway` Gateway, trusts tokens from realm `parasol`, and has two authorization rules:
+
* `approved-agent`: `auth.identity.azp in ['parasol-claims-agent', 'parasol-fraud-agent']`. A call must come through an approved agent; a person's own login token is refused.
* `tool-access-check`, on every `tools/call`: `'tool:' + <tool name>` must be in the token's roles for that MCP server (`resource_access[<server>].roles`).
+
The `unauthorized` response turns each refusal into a readable reason: "*user* may not call *tool*" or "calls must come through an approved agent". The rule lives in the platform, as a Kubernetes resource in Git, not in the agent's code or its prompt.
+
// SCREENSHOT: s1-console-authpolicy.png — Console, Home > Search, gateway-system, AuthPolicy mcp-tool-auth-policy, YAML: the approved-agent and tool-access-check rules

. *What the model is offered.* Same *Search*, project `parasol-secured`, resource `MCPVirtualServer`, open `claims-db`, tab *YAML*.
+
What you should see: `tools: [get_claim, list_claims_by_status, get_claim_history, get_claim_documents]`. No `approve_payout`, for any user: no chat model can pay. That is why rebecca's insisting ended in a proposal.

=== The rule at work

. *Go around the agent.* Rebecca could not get the tool through the chat. Now try what an attacker would: call the gateway directly. In the *Terminal* tab:
+
[source,bash,role=execute]
----
scripts/abuse.sh secured rebecca 1
----
+
What you should see:
+
* `forced at the MCP gateway, rebecca's own token: ... calls must come through an approved agent (got azp=parasol-demo-cli). (HTTP 403)`: the `approved-agent` rule. A login token without an agent does not reach a tool;
* `forced at the MCP gateway, rebecca via parasol-claims-agent: ... rebecca may not call approve_payout. (HTTP 403)`: the `tool-access-check` rule. Even through the approved agent, her token lacks the role.

. *The gateway's own record.* Every decision, allowed or refused, is one line in the MCP gateway's access log, with the user and the agent Authorino verified:
+
[source,bash,role=execute]
----
oc logs -n gateway-system -l gateway.networking.k8s.io/gateway-name=mcp-gateway --since=1h --tail=-1 | grep gateway-decision | grep -E 'user=(rebecca|marcus)' | sed 's/.*status=/status=/'
----
+
What you should see: rebecca's chat calls `status=200 ... user=rebecca agent=parasol-claims-agent ... tool=get_claim`; her forced calls `status=403 ... user=rebecca ... tool=approve_payout`; and marcus's click `status=200 req=[user=marcus agent=parasol-claims-agent] ... tool=approve_payout`. The same tool, two people, two answers: the rule decided, not the model. (A `404` just before a `200` is the agent re-opening its MCP session.)

. *Who acted for whom.* Back in the Keycloak *private window*, *Events*, tab *User events*, event type `TOKEN_EXCHANGE`. Expand the newest rows.
+
What you should see: one row per chat turn, client `parasol-claims-agent`, `username` `rebecca` and `marcus`, `subject_token_client_id` `parasol-portal` (the browser login it acted on) and `client_assertion_sub` `system:serviceaccount:parasol-secured:claims-agent` (the agent's workload identity, no secret).
+
image::s1-keycloak-token-exchange.png["Keycloak admin, realm parasol, Events > User events filtered on TOKEN_EXCHANGE, one row expanded: client parasol-claims-agent, username rebecca, subject_token_client_id parasol-portal, client_assertion_sub system:serviceaccount:parasol-secured:claims-agent"]

. *The dashboard.* Select the *OpenShift Console* tab, *Observe*, *Dashboards (Perses)*, project `openshift-operators`, dashboard *Parasol Assistant Token Spend*, row *Gateway decisions*.
+
What you should see: *Gateway rejections by reason* counts `403 not via an approved agent (MCP gateway)` and `403 role does not allow the tool (MCP gateway)`; *Tool calls by tool, user, agent and status* lists `approve_payout`, `marcus`, `parasol-claims-agent`, `200`. The same decisions as the log, counted per person and agent, ready for an alert.
+
image::s1-dashboard-rejections.png["Console, Observe > Dashboards (Perses), openshift-operators, Parasol Assistant Token Spend, row 'Gateway decisions': the rejections table with both 403 reasons and the tool-calls table with approve_payout / marcus / parasol-claims-agent / 200"]
