The agent reached production the same way any workload should: a pipeline that signs what it builds, an admission control that refuses what is not signed, and an evaluation that blocks a bad version before it ships. These controls live in the pipeline and in MLflow for the parasol-secured workspace.

[NOTE]
.Know: why the lifecycle is a control
====
The message to land is that quality and provenance are enforced, not hoped for. A version that fails the evaluation cannot be promoted, so a regression never reaches a customer. What runs in the secured namespace is provably the image the pipeline built and signed, so an unsigned or tampered image cannot start. The prompt that produced a result is a registered, versioned artifact, so an answer can always be traced back to the exact prompt and model that produced it. For a regulated insurer, that is the difference between an agent you can audit and one you cannot.
====

== The secure build pipeline

One pipeline, `parasol-portal-secure-build`, carries the agent from source to the secured namespace. Its steps run in order:

. build
. scan
. evaluation gate
. keyless sign
. Conforma (Enterprise Contract) verify
. promote

== Signing is keyless

The build signs the three images that make up the agent:

* `parasol-portal`
* `claims-db`
* `policy-docs`

There is no long-lived signing key to store or leak. The signature is bound to the build identity and recorded in a transparency log. The policy that enforces it on the cluster is the `ClusterImagePolicy` named `parasol-portal-must-be-signed`.

. In the *Terminal* tab, run a keyless `cosign verify` against the running secured image.

== Evaluation gates promotion

The agent is evaluated against the golden set of 20 cases before it can be promoted. Each case is scored by deterministic scorers and by judge scorers. The pipeline gate blocks promotion when the score falls below 19 of 20. The runs land in experiment 2 of the parasol-secured MLflow workspace.
