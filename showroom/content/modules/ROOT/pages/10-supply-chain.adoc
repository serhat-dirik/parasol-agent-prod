= 10. Showcase 8: Supply chain, signing and admission
:navtitle: 10. Showcase 8: Supply chain, signing and admission
:toc: macro
:toclevels: 2

toc::[]

The agent reached production the way any workload should: a pipeline that evaluates, signs and verifies what it builds, and an admission policy that refuses anything unsigned. What runs in `parasol-secured` is provably the image the pipeline built.

[NOTE]
.Know: provenance is enforced at the door
====
What runs next to customer data must be the exact image the pipeline built, evaluated and signed. An unsigned or tampered image cannot start in the secured namespace, whoever deploys it.
====

== The business case

[cols="1,4"]
|===
|Who
|The platform team, and anyone who can deploy to the cluster.

|What is at stake
|What runs next to customer data must be exactly what was built, scanned, evaluated and approved. A tampered or unsigned image, or a workload calling an unapproved model, bypasses every other control.

|Without the platform
|Any image can run, and any workload can call any model endpoint it has a key for.

|With the platform
|The pipeline signs and verifies every release, admission refuses unsigned images in the secured namespace, and only approved models are reachable.
|===

== Technical evidence: the secure build pipeline

. Select the *Argo CD* tab and open application `platform-pipeline`.
+
What you should see: the release process is code too. Argo CD keeps the `parasol-portal-secure-build` Pipeline and its Tasks in the state Git describes (Synced, Healthy). A run is an event, not desired state, so runs are not part of the app.

. Select the *OpenShift Console* tab, open *Pipelines*, project `parasol-build`, *Pipeline runs*, then `parasol-portal-release-production`.
+
What you should see: the portal built from source (`build-container`); then in parallel the vulnerability scan (`scan-image`), two signatures (`sign-images` with the cluster key and `keyless-sign` through Trusted Artifact Signer) and the Showcase 5 gate (`agent-eval`); `verify-enterprise-contract` (Conforma) checks the signatures and provenance; only then `promote`, next to `generate-sbom` and `register-model-version`. (On this console version the graph can show a red marker on `promote`'s step once the run is old; the run's status line, *Tasks Completed: 13 (Failed: 0)*, and the `promote` log are the record.)
+
image::sc-pipeline-v1-promoted.png["The release run: build, scan, keyed and keyless signing, Conforma, the evaluation gate, then promote"]

. Open the `keyless-sign` task log.
+
What you should see: `tlog entry created` and `VERIFIED (keyless)` for the portal digest. No long-lived key: the pipeline's workload identity gets a certificate valid for minutes, signs, and the signature lands in the Rekor transparency log. `sign-images` shows the same image signed with the cluster key; admission accepts either.

. Open the `promote` task log.
+
What you should see: first `Prompt pinned: agent-prompt-release = parasol-claims-assistant-system-prompt/1 (parasol-claims-assistant-system-prompt@production, sha256 ...)`, then `PROMOTED: env-secured runs ...parasol-portal@sha256:...` with the prompt version, its sha256 and the model version (`parasol-claims-assistant:production`) the gate evaluated. The release ships the prompt like the image: `agent-eval` registered `gitops/envs/secured/system-prompt.txt` as the version behind `@production` and evaluated it, and `promote` pins exactly that text in the ConfigMap `agent-prompt-release`, the only prompt the secured portal reads. A commit that edits the prompt file changes nothing at run time until the next release has gated and pinned it. Promotion writes nothing to Git: the repository stays read-only for releases. The task pins the signed digest on the Argo CD Application `env-secured` and waits until Argo CD reports it Synced and Healthy.

. Select the *Argo CD* tab, open application `env-secured`, click *Details* and select the *Parameters* tab.
+
What you should see: under *Images*, the `parasol-portal` override with the promoted digest. The *Summary* tab carries the audit trail as annotations: `parasol.example/promoted-digest`, `promoted-by` (the TaskRun), `prompt-ref`, `prompt-version` (the registry version pinned), `prompt-sha256` (the digest of the pinned prompt text) and `model-ref`. *History and rollback* lists the sync that rolled it out. The `prompt-version` here (`parasol-claims-assistant-system-prompt/1`, the version behind `@production`) is the same value every live chat trace carries as its `prompt` tag, and `prompt-sha256` matches the trace's `prompt_sha256` (xref:07-scenario5-eval-gate.adoc[07. Showcase 5]): release record and runtime evidence agree.

== Technical evidence: admission refuses an unsigned image

The `ClusterImagePolicy` `parasol-portal-must-be-signed` admits only portal images signed by the pipeline.

. In the *OpenShift Console* tab, open the policy. Direct link: link:{console_url}/k8s/cluster/policy.sigstore.dev~v1beta1~ClusterImagePolicy/parasol-portal-must-be-signed/yaml[ClusterImagePolicy parasol-portal-must-be-signed,window=_blank].
+
What you should see: the image pattern for the portal and the two accepted signing authorities (keyless and the cluster key).

. In the *Terminal* tab, try to run an unsigned and a signed portal image in the admission demo namespace:
+
[source,bash,role=execute]
----
scripts/signing-demo.sh
----
+
What you should see:
+
* the *unsigned* image is refused by the admission webhook, with a message naming the missing signature;
* the *signed* image is admitted and its pod is created;
* the script removes its test pods at the end.
+
Signatures, the admission decision and the promote history on `env-secured` together answer "what runs in production, and who let it in".

== Technical evidence: only approved models

Shadow AI: a developer is in a hurry, has a personal key for a public model API, and points a workload at it directly, around the platform's model gateway. Same model swap, different blast radius. On the secured side the image can be signed and the prompt gated, and still the question is: which models can this workload reach at all?

. *Unsecured.* In the *Terminal* tab, from the unsecured portal pod, call a public model API without a key:
+
[source,bash,role=execute]
----
oc exec -n parasol-free deploy/portal -- curl -sS -o /dev/null -w '%{http_code}\n' --max-time 8 https://api.openai.com/v1/models
----
+
What you should see: `401`. The endpoint answered and only wants a key: with the developer's own key in an environment variable, this workload would talk to an unapproved model, outside every budget, guardrail and trace. The unsecured namespace also holds the upstream provider key itself (Secret `maas-credentials`).

. *Secured.* The same call from the secured portal pod:
+
[source,bash,role=execute]
----
oc exec -n parasol-secured deploy/portal -- curl -sS -o /dev/null -w '%{http_code}\n' --max-time 8 https://api.openai.com/v1/models
----
+
What you should see: `000` and `curl: (28) Failed to connect to api.openai.com port 443: Connection timed out`. No key would help: the packet never leaves the namespace.

. *Why.* Select the *OpenShift Console* tab, project `parasol-secured`, *Networking*, *NetworkPolicies*.
+
What you should see: `default-deny` (every pod, ingress and egress), then one allow-list per workload: `portal` and `parasol-agent` reach only the MCP gateway and Keycloak (by their in-cluster Services, not through the router), the model gateway (`parasol-model-gateway`) and the OTel collector; `guardrails` reaches only the detectors, the in-cluster MaaS gateway and OTel; the MCP servers reach only OTel (and Keycloak's signing keys). There is no rule to the internet.
+
image::sc-networkpolicies-secured.png["Console, project parasol-secured, NetworkPolicy portal: egress only to the MCP gateway, Keycloak, the model gateway, OTel and claims-db"]

. *The drop is on record.* The namespace carries `k8s.ovn.org/acl-logging: {"deny": "alert"}`, so OVN logs every connection a NetworkPolicy drops on the pod's node. From a workstation as an administrator (the Terminal's identity may not read node logs):
+
[source,bash]
----
node=$(oc get pod -n parasol-secured -l app=portal -o jsonpath='{.items[0].spec.nodeName}')
oc adm node-logs $node --path=ovn/acl-audit-log.log | grep 'NP:parasol-secured:Egress' | tail -3
----
+
What you should see: `name="NP:parasol-secured:Egress", verdict=drop, severity=alert, ... nw_src=<the portal pod IP>, nw_dst=<the public address>, tp_dst=443`. Without the annotation, NetworkPolicy drops are not logged at all; the namespace in this demo opts in.

. *Only registered models, only MaaS keys.* Select the *OpenShift Console* tab, project `models-as-a-service`, *Home*, *Search*, resource `MaaSModelRef`: the models the platform serves (the assistant's model and the guard model chosen at setup; tested with `qwen3-14b` and `granite-guardian-3-1-8b`), each *Ready* behind `maas-default-gateway` and backed by an `ExternalModel` whose upstream provider key lives in that project only. In the *OpenShift AI* tab, *Settings*, *MaaS governance* lists the subscriptions that may use each one. Then, in the *OpenShift Console* tab, project `parasol-secured`, *Secrets*: `maas-credentials` and `maas-portal-keys` hold *MaaS* keys, each bound to a subscription with its own token limit (xref:06-scenario4-night-shift.adoc[06. Showcase 4]); no provider key is in the namespace. Every model call goes portal -> model gateway -> guardrails proxy -> MaaS, and MaaS routes only to the models registered in it: a request for any other model name finds no route.
+
image::sc-maas-models.png["Console, project models-as-a-service, MaaSModelRefs: the two models the platform serves, each Ready behind maas-default-gateway"]

. *No path around the guardrails.* The secured portal reaches Keycloak and the MCP gateway by their in-cluster Services, so its policy has no rule to the cluster's router, and with it none to the platform's own MaaS route. In the *Terminal* tab:
+
[source,bash,role=execute]
----
oc exec -n parasol-secured deploy/portal -- curl -sS -o /dev/null -w '%{http_code}\n' --max-time 8 https://maas.apps.$(oc get dns cluster -o jsonpath='{.spec.baseDomain}')/v1/models
----
+
What you should see: `000`, `curl: (28) Connection timed out`. Even with a MaaS key the portal cannot skip the model gateway and the guardrails proxy: the only model path it has is portal -> model gateway -> guardrails proxy -> MaaS.

== Conclusion

The showcases and the incident made one argument. The unsecured and the secured portal are the same image running the same model. The difference is the platform around it, and every piece of that platform is a product an operator already knows:

* Identity on every tool call: Keycloak and the MCP gateway.
* Identity on data: retrieval runs as the user, down to row-level security in the database.
* A document is data, not a command: guardrails and the Read-Propose-Act gate.
* Budgets and alerts with a name: OpenShift AI Models-as-a-Service, Connectivity Link, and the OpenShift console.
* Only approved models: egress only to the platform's gateways, provider keys only in MaaS, only registered models routed.
* Quality and provenance enforced: the evaluation gate, signing and admission.
* A tool is a supply chain too: the MCP gateway federates only reviewed registrations, and the tool scanner pins and reads every tool description.
* The sandbox has a front door: access is identity-bound, and the operator can switch one agent off in Keycloak or every agent off at the gateways, each with one command.
