= 06. Showcase 4: The night shift
:navtitle: 06. Showcase 4: The night shift
:toc: macro
:toclevels: 2

toc::[]

An outsourced night-shift contractor's account (or its leaked token) is scripted at 3 a.m. to loop long requests and drain the model budget. Unsecured, the shared key burns all night. Secured, the off-topic junk is refused for free, only that account is throttled, an alert names the user, and the operator has a layered kill switch, from one person to the whole cluster, each level one command.

The script `scripts/night-shift.sh` plays the scripted account. It logs in as `nina.contractor` (Nina Patel, a contractor with read-only claim tools), sends two off-topic requests, then loops long on-topic requests, printing the HTTP status, the caller and the token spend of each. It stops at the first usage-limit response and has a hard ceiling, so a stray run cannot drain the model key.

[NOTE]
.Know: budgets and alerts with a name
====
An agent on a shared key is an open invoice: anyone who can reach the chat can spend the budget, and nobody can say who did. On the platform, each tier has its own budget, so the contractors are throttled while everyone else keeps working, and spend is attributed to a user and an agent, so the alert says who.
====

== The business case

[cols="1,4"]
|===
|Who
|Nina Patel, an outsourced night-shift contractor (or whoever holds her leaked token), and the claims staff who need the assistant in the morning.

|What is at stake
|Denial of wallet. Every model call costs money. One account looping long requests all night burns the shared budget, and in the morning the assistant is down for everyone. Without attribution nobody can say who spent it, or stop only that account.

|Without the platform
|One shared key, no per-user limit. The budget is gone by morning, and no dashboard or alert says who spent it.

|With the platform
|Off-topic requests are refused for 0 tokens, only Nina's account is throttled at her tier's limit, an alert names her and the agent, and the operator can switch off the user, one agent, one tier, all of Parasol or, in an emergency, every tool and model call.
|===

== Before you start

This showcase runs on its own, in any order with the others.

* Personas: `nina.contractor` (the night-shift contractor, played by the script) and `rebecca`; passwords equal the user names.
* State: every kill switch is on (`scripts/kill-switch.sh status`: no user disabled, both agents enabled, every subscription on, the gateways up), and her token budget is full. If an earlier run changed any of them, undo it as in *Reset after this showcase* below.

== The operator's night

One flow, the way an operator lives it: the script runs, the alert fires, the operator finds out who and through what, confirms only that account is throttled, looks at what it did, and switches it off at the narrowest level that works. Every step says where to look and what to check.

=== 1. 3 a.m.: the script runs

. Unsecured first. In the *Terminal* tab, run the night shift against the unsecured portal:
+
[source,bash,role=execute,subs=attributes]
----
scripts/night-shift.sh 40 portal-free.{domain}
----
+
What you should see: every request is answered; there is no per-user limit on the shared key. Left running all night, the budget is gone by morning and the assistant answers the claims staff with "budget exhausted". Look for this traffic on the platform: there is none to find. The unsecured portal calls the model provider directly with a key from a Secret, so no subscription, budget, dashboard or alert covers it. Denial of wallet, and nobody was watching.

. Now the secured portal. Give `nina.contractor` a full token budget again, then run the same script (the secured portal is the default target):
+
[source,bash,role=execute]
----
scripts/reset.sh
scripts/night-shift.sh 40
----
+
What you should see:
+
* the off-topic requests get a polite refusal from the topic guardrail at *0 tokens*;
* the on-topic loop keeps hammering, and the per-user spend climbs;
* after the contractor tier's token limit (Nina is its only member), the response reads "you have reached your usage limit (429)" and the script stops.

=== 2. The alert fires: who, through which agent

. Select the *OpenShift Console* tab, *Observe*, *Alerting*, project `parasol-secured`, and open the firing `ParasolAssistantTokenSpendHigh`.
+
What you should see: the labels `user=nina.contractor`, `agent=parasol-claims-agent`, `namespace=parasol-secured`, and the description "Agent parasol-claims-agent on behalf of user nina.contractor is spending ... tokens/min", followed by the switches to use. The alert needs both the burst above the line and the usage-limit 429, so staff asking a few questions back to back do not trigger it.
+
image::s4-alert-firing.png["Console, Observe > Alerting, ParasolAssistantTokenSpendHigh firing: agent parasol-claims-agent on behalf of user nina.contractor, with the operator responses in the description"]

. Confirm it from the portal's own counters, per person and agent:
+
[source,bash,role=execute]
----
scripts/evidence.sh spend
----
+
What you should see: `nina.contractor via parasol-claims-agent` with a large token count, and under `refused by the platform` the line `nina.contractor via parasol-claims-agent  usage_limit` with a count. No `usage_limit` line for `rebecca`. Every token is booked to a person and an agent; that is why the platform can stop one account and leave the others alone.

. Watch it. *Observe*, *Dashboards (Perses)*, project `openshift-operators`, *Parasol Assistant Token Spend*; set *User* to `nina.contractor` and `rebecca`, so the earlier showcases' chats do not crowd the view.
+
What you should see, in the row *Token spend*:
+
* *Token spend per user and agent* climbing as `nina.contractor via parasol-claims-agent` past the red 5000 tokens/min line for the whole loop, while `rebecca via parasol-claims-agent` shows only a short blip;
* *Tokens by user and agent* with `nina.contractor`, `parasol-claims-agent`, `secured` on top;
* *Tokens by tier and agent*: the contractor tier (`parasol-contractor`) against the staff tier (`parasol-stage`), the cost per team;
* *ParasolAssistantTokenSpendHigh: alert state* stepping to `firing nina.contractor via parasol-claims-agent`.
+
In the row *Gateway decisions*, *Gateway rejections by reason* has `429 usage limit (MaaS token budget)` for `nina.contractor` via `parasol-claims-agent`.
+
image::s4-dashboard-tiers.png["Console, Parasol Assistant Token Spend, row Token spend after night-shift.sh: nina.contractor above the 5000 tokens/min line, the alert firing, and Tokens by tier and agent with contractor (parasol-contractor) next to staff (parasol-stage)"]

=== 3. Only that account is throttled

. Select the *Portal secured* tab, sign in as `nina.contractor`, open her claim *CLM-1031* and ask a question.
+
What you should see: "You have reached your usage limit (429). Please try again later." The account, not the portal, is out of budget.

. Sign out, log in as `rebecca`, open any claim and ask a question.
+
What you should see: rebecca keeps working normally.

. Why: the rule is a Models-as-a-Service subscription per tier, not code in the agent.
+
[source,bash,role=execute]
----
scripts/evidence.sh tiers
----
+
What you should see: `parasol-contractor`, owned by the group `parasol-contractor`, with a small token budget (for example `20000 tokens / 10m`), next to the staff tier `parasol-stage` with a larger one. The MaaS gateway counts the tokens and answers 429 at the limit, before the model is called. The same in the *OpenShift AI* tab, *Settings*, *MaaS governance*; *Gen AI studio*, *API keys* shows when each tier's key was last used.
+
image::s4-maas-subscriptions.png["MaaS governance: the contractor, stage and guard subscriptions, each Ready with its own priority and token limit"]

=== 4. What the account did

. Select the *MLflow* tab, workspace `parasol-secured`, experiment `parasol-portal-chat`, *Traces*, then *Filters*, field *Tags*, key `team`, value `contractors`, *Apply filters*.
+
What you should see: nina's turns, each with the question and the answer as the trace's *Request* and *Response*. Open one, tab *Assessments*: the AgenticOps checks the CronJob `agenticops` (project `observability`, every 10 minutes) logged on the turn: `loop`, `excess_steps`, `unknown_tool` and `pii_in_tool_args`, each `true` or `false` with its reason, and the tag `team` `contractors`. For a sample of turns the judge model, called through MaaS, adds `goal_achieved` with a one-sentence rationale. The same checks run on every agent turn, not only on alerts. The latest runs, from the *Terminal* tab: `scripts/evidence.sh agenticops`.
+
image::s4-mlflow-contractor-turns.png["MLflow, workspace parasol-secured, experiment parasol-portal-chat, Traces filtered on the tag team = contractors: nina.contractor's night-shift turns with Request and Response, the excess_steps and goal_achieved assessments"]

=== 5. Switch it off, narrowest first

The kill switch has five levels, from one person to the whole cluster. Pick the narrowest one that stops the problem. Each is one command, each is undone with `on`, nothing in Git changes, and `scripts/reset.sh` undoes all of them.

[cols="1,3,2",options="header"]
|===
|Level |What it stops |Where it runs

|`user <name>`
|One person. The user is disabled in Keycloak (realm `parasol`) and signed out: no login, no token exchange, so no tool call on their behalf. Everyone else keeps working.
|*Terminal*, or Keycloak admin

|`agent <agent>`
|One agent (`claims-agent` or `fraud-agent`). Its Keycloak client is disabled, so it can no longer act for anyone. Other agents and every user keep working.
|*Terminal*, or Keycloak admin

|`tier <subscription>`
|One MaaS subscription, for example `parasol-contractor`. Every key minted for it is refused, within about 60 seconds. No other tier changes.
|administrator's workstation

|`parasol`
|Every Parasol MaaS subscription, the same way: no Parasol model call, from any portal or agent.
|administrator's workstation

|`break-glass`
|The MCP gateway and the cluster's MaaS gateway scaled to 0: no tool call and no model call for any consumer on the cluster.
|*Terminal* (MCP gateway only); administrator's workstation (both)
|===

Where every switch stands, in the *Terminal* tab:

[source,bash,role=execute]
----
scripts/kill-switch.sh status
----

What you should see: four short sections, `users (realm parasol, disabled)`, `agents`, `MaaS subscriptions (tier / parasol)` and `break glass`. Before you act: no user disabled, both agents `enabled=true`, every subscription `on`, the gateways at their normal replicas.

image::s4-kill-switch-status.png["Terminal: scripts/kill-switch.sh status with one level switched off: nina.contractor disabled in realm parasol, both agents enabled, every MaaS subscription on, the MCP gateway at 2 replicas (the cluster MaaS gateway is not readable from this Terminal)"]

==== One user

The problem is one account: the night-shift contractor.

. In the *Terminal* tab:
+
[source,bash,role=execute]
----
scripts/kill-switch.sh user nina.contractor off
----
+
What you should see: `user nina.contractor enabled=false`, then `user nina.contractor signed out`. The same switch is in the Keycloak admin *private window* (page 02): realm `parasol`, *Users*, `nina.contractor`, *Enabled*.

. Run the night shift once more:
+
[source,bash,role=execute]
----
scripts/night-shift.sh 3
----
+
What you should see: the script cannot log in as `nina.contractor`. Everyone else keeps working.

. Undo it:
+
[source,bash,role=execute]
----
scripts/kill-switch.sh user nina.contractor on
----

==== One agent

Disable an agent the way you disable a user. The claims assistant's identity is the Keycloak client `parasol-claims-agent`; with it off, Keycloak refuses the agent's own sign-in, so it can no longer act on behalf of anyone. Other agents and every user keep their access.

. In the *Terminal* tab (or, in the Keycloak admin *private window*, *Clients*, `parasol-claims-agent`, *Enabled* off):
+
[source,bash,role=execute]
----
scripts/kill-switch.sh agent claims-agent off
----

. Select the *Portal secured* tab, sign in as `rebecca`, open any claim and ask a question.
+
What you should see: the chat answers at once with the red notice "This assistant has been disabled by an operator." No tool runs and the model is not asked: the portal checks the agent's identity at the start of every turn. How fast the switch bites: on the very next chat turn through the portal; a token the agent obtained before the switch, wherever it was copied to, expires within 5 minutes (the agent clients' token lifespan).

. Show who was refused:
+
[source,bash,role=execute]
----
scripts/kill-switch.sh agent claims-agent status
----
+
What you should see: `parasol-claims-agent enabled=false` and the recent refusals from Keycloak's events: `TOKEN_EXCHANGE_ERROR` with `error=client_not_found` (a disabled client is unknown to Keycloak) and `sa=system:serviceaccount:parasol-secured:claims-agent`, the agent's own ServiceAccount. The MCP gateway sees nothing: the agent never got a token to present.

. Undo it:
+
[source,bash,role=execute]
----
scripts/kill-switch.sh agent claims-agent on
----
+
What you should see: the next question in the *Portal secured* tab is answered normally.

Switching off `fraud-agent` instead shows the other half of the story: rebecca's "Run a fraud check on this claim." on CLM-1004 still calls `fraud_check`, but the fraud agent cannot act for her, so the answer says the fraud check could not be completed, while the claims assistant keeps answering her other questions.

==== One tier, or all of Parasol

When the spend comes from a whole group of users, cut their model budget at Models-as-a-Service. These switches change MaaS subscriptions, a cluster administrator's resources, so they run from an administrator's workstation, not from this Terminal:

[source,bash]
----
scripts/kill-switch.sh tier parasol-contractor off
scripts/kill-switch.sh tier parasol-contractor status
----

What you should see: `parasol-contractor OFF (saved owner ...)` and `takes effect within about 60 s`. The subscription's owner groups are set aside, so every key minted for the contractor tier is refused; the staff tier `parasol-stage` is untouched, so rebecca keeps working. In the *Terminal* tab, `scripts/evidence.sh tiers` shows the same subscription as `SWITCHED OFF (kill switch)`. Undo with `scripts/kill-switch.sh tier parasol-contractor on`. `scripts/kill-switch.sh parasol off` does the same for every Parasol subscription at once.

==== Break glass

When you cannot tell what is misbehaving, stop every tool call and every model call on the cluster. In the *Terminal* tab:

[source,bash,role=execute]
----
scripts/kill-switch.sh break-glass off
----

What you should see: the MCP gateway `gateway-system/mcp-gateway-openshift-default` at `replicas=0`. From this Terminal the cluster's MaaS gateway is refused (its scale is an administrator's action); from an administrator's workstation the same command scales both. Select the *Portal secured* tab and ask about a claim: the assistant can no longer reach any tool. In the *OpenShift Console* tab, project `parasol-secured`, the portal and agent pods are still *Running*: they simply reach nothing.

Bring it back:

[source,bash,role=execute]
----
scripts/kill-switch.sh break-glass on
----

What you should see: the gateway back at its normal replicas; the next question is answered.

== Reset after this showcase

Refill the token budgets, put the claims back, and switch every level back on (users, agents, MaaS subscriptions, gateways):

[source,bash,role=execute]
----
scripts/reset.sh
----

To undo one switch only: `scripts/kill-switch.sh <level> ... on`, for example `scripts/kill-switch.sh agent claims-agent on`.

The `ParasolAssistantTokenSpendHigh` alert resolves on its own about 20 minutes after the spend stops.
