= AI Agents: From localhost to Production

Anyone can stand up an AI agent on a laptop in an afternoon. Running that same agent in production, where real people use it, feed it real documents and try to abuse it, is where the hard problems live. This guide is the presenter's script for a live demonstration of that gap, and of how an OpenShift-based platform closes it.

== The premise: the Parasol claims assistant

Parasol Insurance runs a claims portal (Quarkus and React/PatternFly, Keycloak login). Beside each claim sits a chat assistant. It is not a chatbot: it is a tool-using agent that calls MCP tools to read claims, policy documents and Parasol's internal knowledge base, and to approve payouts.

An agent that can move money is an agent worth abusing.

== One image, two portals

The same portal image runs twice on one cluster, over separate, identically seeded claims databases:

* *Portal unsecured* (`portal-free`): the laptop setup lifted into a namespace. Nothing sits between the agent and its tools, and nothing between the agent and the model but an API key in a Secret.
* *Portal secured* (`portal`): the same image behind a layered sandbox: namespace isolation, Keycloak identity on every tool call, per-identity tool authorization at an MCP gateway, content guardrails (NeMo Guardrails, applied by the gateways), Models-as-a-Service governance with per-tier token budgets, tracing, token metrics and AgenticOps checks, a kill switch in layers (one user, one agent, one tier, all of Parasol, break glass), and a signed-image supply chain with admission control.

You demo the *same claim* with the *same request* on each portal. The only variable is the platform.

== The showcases

*Business showcases*: what a user, a customer or a document can make the assistant do. Each one runs on both portals, unsecured first, then secured, then the platform's own records.

. *The overstepping colleague.* A claims adjuster pushes the assistant to approve a payout the adjuster has no authority to approve. Ends with the audit trail: one payout, reconstructed from the platform's records, from the claim back to the signed release.
. *The customer's document.* An uploaded repair estimate is inflated to USD 84,000 and carries a hidden note addressed to the assistant.
. *The confidential document.* The assistant searches Parasol's knowledge base, where some documents are for everyone, some for claims staff and some for claims managers only, and an adjuster asks about plans affecting her own team.

*Operations*: how an operator watches agents and stops them.

[start=4]
. *The night shift.* An outsourced night-shift contractor's account (or its leaked token) is scripted at 3 a.m. to drain the token budget; the operator sees it, names it and switches it off, one layer at a time.

*Agent delivery lifecycle*: how an agent, its prompt and the tools it uses reach production.

[start=5]
. *Supply chain, signing and admission.* The release pipeline builds, scans and signs the portal; admission runs only signed images, and secured workloads reach only approved models.
. *The evaluation gate.* A developer shortens the system prompt; the release evaluates it against a golden set and refuses it, although with the platform on it scores about as well as production.
. *Third-party tools.* A vendor's currency-conversion tool; later its description changes, without a new version, and asks the assistant to approve payouts.

Unsecured, the business showcases and the third-party tool cause harm. Secured, a *different* layer stops each, and the platform consoles show why. Each showcase stands on its own: run any of them, in any order, using its *Before you start* and *Reset* steps.

The business showcases follow one shape: *The business case* (who, what is at stake, the outcome without and with the platform), the *Scenario walkthrough* on the unsecured portal and then the secured one, a short *Evidence demo* and *Evidence details* for curious minds, and an *Evidence checklist* to close on. The operations and delivery showcases follow the operator's or the pipeline's own steps: run it, look, check.

[NOTE]
.The messages to land
====
. Identity on every tool call, and on the data the agent retrieves.
. A document is data, not a command.
. Read, propose, act: a person with the right role makes every write.
. Budgets and alerts with a name.
. The sandbox has a front door: identity-bound access, not a wall.
. A tool is a supply chain too: only reviewed, pinned tools reach the agent.
====
