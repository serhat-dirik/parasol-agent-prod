= 09. Supply chain: signing and admission
:navtitle: 09. Supply chain
:toc: macro
:toclevels: 2

toc::[]

The agent reached production the way any workload should: a pipeline that evaluates, signs and verifies what it builds, and an admission policy that refuses anything unsigned. What runs in `parasol-secured` is provably the image the pipeline built.

[NOTE]
.Know: provenance is enforced at the door
====
What runs next to customer data must be the exact image the pipeline built, evaluated and signed. An unsigned or tampered image cannot start in the secured namespace, whoever deploys it.
====

== Show: the secure build pipeline

. Select the *Argo CD* tab and open application `platform-pipeline`.
+
What you should see: the release process is code too. Argo CD keeps the `parasol-portal-secure-build` Pipeline and its Tasks in the state Git describes (Synced, Healthy). A run is an event, not desired state, so runs are not part of the app.

. Select the *OpenShift Console* tab, open *Pipelines*, project `parasol-build`, *Pipeline runs*, then `parasol-portal-release-production`.
+
What you should see: the portal built from source (`build-container`); then in parallel the vulnerability scan (`scan-image`), two signatures (`sign-images` with the cluster key and `keyless-sign` through Trusted Artifact Signer) and the Scenario 4 gate (`agent-eval`); `verify-enterprise-contract` (Conforma) checks the signatures and provenance; only then `promote`, next to `generate-sbom` and `register-model-version`.
+

. Open the `keyless-sign` task log.
+
What you should see: `tlog entry created` and `VERIFIED (keyless)` for the portal digest. No long-lived key: the pipeline's workload identity gets a certificate valid for minutes, signs, and the signature lands in the Rekor transparency log. `sign-images` shows the same image signed with the cluster key; admission accepts either.

. Open the `promote` task log.
+
What you should see: `PROMOTED: env-secured runs ...parasol-portal@sha256:...` with the prompt (`parasol-claims-assistant-system-prompt@production`) and model version (`parasol-claims-assistant:production`) the gate evaluated. Promotion writes nothing to Git: the repository stays read-only for releases. The task pins the signed digest on the Argo CD Application `env-secured` and waits until Argo CD reports it Synced and Healthy.

. Select the *Argo CD* tab, open application `env-secured`, click *Details* and select the *Parameters* tab.
+
What you should see: under *Images*, the `parasol-portal` override with the promoted digest. The *Summary* tab carries the audit trail as annotations: `parasol.example/promoted-digest`, `promoted-by` (the TaskRun), `prompt-ref` and `model-ref`. *History and rollback* lists the sync that rolled it out. The `prompt-ref` here is the same `parasol-claims-assistant-system-prompt@production` every live chat trace carries as its `prompt` tag (xref:07-scenario5-eval-gate.adoc[06. Scenario 4]): release record and runtime evidence agree.

+
What you should see: the secured portal runs exactly that pinned digest; admission verified its signature when Argo CD rolled it out.

== Show: admission refuses an unsigned image

The `ClusterImagePolicy` `parasol-portal-must-be-signed` admits only portal images signed by the pipeline.

. In the *OpenShift Console* tab, open the policy. Direct link: link:{console_url}/k8s/cluster/policy.sigstore.dev~v1beta1~ClusterImagePolicy/parasol-portal-must-be-signed/yaml[ClusterImagePolicy parasol-portal-must-be-signed,window=_blank].
+
What you should see: the image pattern for the portal and the two accepted signing authorities (keyless and the cluster key).

. In the *Terminal* tab, try to run an unsigned and a signed portal image in the admission demo namespace:
+
[source,bash,role=execute]
----
scripts/signing-demo.sh
----
+
What you should see:
+
* the *unsigned* image is refused by the admission webhook, with a message naming the missing signature;
* the *signed* image is admitted and its pod is created;
* the script removes its test pods at the end.
+
Signatures, the admission decision and the promote history on `env-secured` together answer "what runs in production, and who let it in".
+

== Conclusion

The six scenarios made one argument. The unsecured and the secured portal are the same image running the same model. The difference is the platform around it, and every piece of that platform is a product an operator already knows:

* Identity on every tool call: Keycloak and the MCP gateway.
* Identity on data: retrieval runs as the user, down to row-level security in the database.
* A document is data, not a command: guardrails and the Read-Propose-Act gate.
* Budgets and alerts with a name: OpenShift AI Models-as-a-Service, Connectivity Link, and the OpenShift console.
* Quality and provenance enforced: the evaluation gate, signing and admission.
* A tool is a supply chain too: the MCP gateway federates only reviewed registrations, and the tool scanner pins and reads every tool description.
* The sandbox has a front door: access is identity-bound, and the kill switch is one change on the Argo CD Application.
