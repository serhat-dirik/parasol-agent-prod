This module is the map: the application, the people, the models, and the layer that stops each showcase. Everything here is declared in Git and synced by Argo CD.

[NOTE]
.Know: why the architecture is the story
====
Nothing here is exotic. It is one ordinary insurance application with a chat assistant, deployed twice; the only difference is the platform around it. Every control maps to money: an unauthorized payout is unrecoverable spend, a shared model key with no limit is an open invoice, and an unsigned change is one nobody can account for.
====

== The application

The Parasol claims portal is a Quarkus backend with a React/PatternFly front end and a Keycloak login. It lists claims; each claim has a detail page with a *Summary* tab (the customer's account, photos and, at the bottom, the documents the customer attached), an *Insurance* tab, a *History* tab (the claim's timeline) and a chat panel. The chat is the agent.

Its tools come from MCP servers:

* *claims-db*: read a claim and its history, read the documents attached to it (`get_claim_documents`), propose a payout (`propose_payout`) and approve one (`approve_payout`, the write).
* *policy-docs*: read the Parasol policy documents.
* *fraud-check* (secured only): a second agent behind the same gateway that scores a claim's fraud risk.

Every tool call streams into the chat as a chip, so you see what the agent did:

* a normal chip, for example `approve_payout(CLM-1001)`;
* a red chip for a refused call, for example `403: approve_payout is not permitted for rebecca (MCP gateway)`, or `get_claim_documents: refused by the MCP gateway (HTTP 500)` when the gateway's guardrails block what a tool returned;
* an amber banner for a guardrail detection on the model path (the user's message or the answer);
* a grey `personal data masked` chip when guardrails mask personal data.

== The models

The models are hosted outside the cluster, behind any OpenAI-compatible endpoint, and reached through OpenShift AI Models-as-a-Service (MaaS). No GPU in the cluster. Each one is chosen at setup; these are the tested defaults:

* `qwen3-14b`: the agent model. *Both* portals run it. It emits structured tool calls and it obeys an instruction hidden in a document, which is what makes Showcase 2's unsecured side pay. The same model, with a short yes/no prompt, is the guardrails' injection judge on tool results (set in the NeMo Guardrails manifest, not at setup).
* `gpt-oss-120b`: the evaluation judge in Showcase 5 and the sampled judge of the AgenticOps checks.
* `granite-guardian-3-1-8b`: the guard-tier model, registered in MaaS and in the model registry. It is *not* on the live request path: on Parasol's documents it lost the injection test to the `qwen3-14b` judge (it missed reworded notes, or flagged ordinary claim records).

The agent never holds the upstream model key. MaaS holds it, and gives each consumer its own MaaS key bound to a subscription with a token budget. MaaS meters by the key's owner, and the secured portal holds one key per tier (staff, contractor), so MaaS sees a *tier*, not a person. Who spent what, per person and per agent, comes from the portal's own metrics and the traces.

== The secured request paths

* *Model:* portal -> guardrails proxy -> OpenShift AI MaaS -> external endpoint. The proxy is thin glue: it asks NeMo Guardrails (config `parasol-chat`) to check the user's message before the model (injection phrases and off-topic are refused, personal data is masked) and the answer after it (the confidential marker for non-managers is withheld, outside links are removed). MaaS checks the key, picks its subscription and enforces the tier's token budget.
* *Tools:* portal -> MCP gateway (`https://mcp.{domain}/mcp`: one URL for all four servers; each of the portal's MCP clients asks for its own named tool set, a _virtual server_, such as the four claims read tools) -> claims-db, policy-docs, fraud-check, knowledge-base. The assistant acts *on behalf of* the user: on every call it exchanges the user's Keycloak token for one issued to the agent's own identity (`parasol-claims-agent`; user = `sub`, agent = `azp`), carrying only the tool roles that are both the user's and inside the agent's ceiling. The agent authenticates to Keycloak with its pod's ServiceAccount token, so there is no client secret. The gateway accepts only tokens from approved agents, filters the tool list per identity and enforces a per-tool AuthPolicy. For claims-db it also sends every tool result to NeMo Guardrails (config `parasol-tool-results`) and refuses a result that carries instructions for the assistant. The fraud-check agent does the same again (`parasol-fraud-agent`, read-only) when it reads the claim.

* *Knowledge:* the knowledge-base server checks the same on-behalf-of token itself (signature, issuer, audience) and searches only the documents the user's Keycloak groups may read; PostgreSQL row-level security on the documents table enforces the same rule a second time, below the application.

The unsecured portal skips all of it: a shared model key, and tools called with no authorization and no record.

== Read, propose, act

The model is never shown `approve_payout`: its claims tool set holds only the read tools, plus a local `propose_payout` that draws a proposal card and moves no money. So the assistant can only *propose*, whatever a person or a document asks. The write is a claims manager's *Approve* click, which calls `approve_payout` directly.

What enforces it is the gateway's role check on every call, not the tool set: the gateway serves `approve_payout` only to a token that carries the Keycloak role `tool:approve_payout` (claims managers only) and was exchanged by an approved agent. No token is a 401, a person's own login token is a 403, and an adjuster's forced call is a 403.

== Which layer stops which showcase

[cols="1,2,2",options="header"]
|===
|Layer |Defends |Component

|1 Isolation
|the blast radius of all showcases
|Namespace, ResourceQuota, NetworkPolicy, restricted pod security, no Kubernetes API token; an AdminNetworkPolicy so only the MCP gateway reaches policy-docs, which the OpenShift AI MCP lifecycle operator runs

|2 Identity
|Showcases 1 and 3
|Keycloak: the user's identity plus the agent's own (ServiceAccount, no secret), joined by token exchange on every tool call; the user's groups decide which documents retrieval may search, down to PostgreSQL row-level security

|3 Tool authorization
|Showcase 1
|MCP gateway (Connectivity Link 1.5): per-identity tool list, per-tool AuthPolicy

|4 Guardrails
|Showcases 2, 3 and 4
|NeMo Guardrails (one service, `parasol-nemo`), applied by the gateways: the MCP gateway checks claims-db tool results (injection phrases, then a `qwen3-14b` judge through MaaS) and refuses a document with instructions; the guardrails proxy checks the model path (injection and off-topic refused, personal data masked, the confidential marker withheld, outside links removed)

|5 Model governance
|Showcase 4
|OpenShift AI MaaS: per-tier subscriptions, auth policies, keys and token budgets enforced by Connectivity Link; MaaS meters per tier, the portal's metrics and the traces name the person

|6 Lifecycle gate
|regressions and unsigned images
|Tekton pipeline (build, scan, evaluation gate, sign, verify, promote) and Sigstore admission policy

|7 Observability and control
|Showcases 3 and 4, knowing and stopping
|OpenTelemetry to Tempo (every span) and MLflow (agent turns only, with the full conversation, one session per user, AgenticOps checks), token metrics and an alert, and a kill switch in layers: one user, one agent, one tier, all of Parasol, break glass
|===

== Where it shows in OpenShift AI

The platform's own screens list what the demo runs. In the *OpenShift AI* tab:

* *AI hub* > *Models* > *Registry*: the three models, each registered as served by MaaS (agent, guard and judge), next to the evaluated claims-assistant versions.
* *AI hub* > *MCP servers* > *Catalog*, source *Parasol MCP servers*: claims-db, policy-docs and the others, with their tools and which ones write.
* *AI hub* > *Agents* > *Catalog*, source *Parasol agents*: the claims agent and the fraud-check agent, what they run on and which tools they reach.
* *Gen AI studio* > *AI asset endpoints* > *MCP servers*: the Parasol MCP gateway, one endpoint for all four servers.
* Project `parasol-playground` > *Gen AI studio* > *Playground*: the dashboard's own OGX server with the agent and judge models (through MaaS) and the Parasol MCP gateway. The gateway lists tools only for a token an approved agent obtained for a person (`scripts/agent-token.sh rebecca`), pasted in the playground's authorize dialog; the playground's own sign-in token is not one.

NOTE: The Parasol agents are Quarkus LangChain4j applications, not OGX agents. In OGX 1.2.5 (OpenShift AI 3.5) a
tool call the gateway refuses ends the whole turn; upstream OGX 1.5 turns it into one failed tool call the agent can
report, but without the gateway's reason yet. When an OpenShift AI release ships it, the same gateway controls apply
to an OGX-built agent unchanged: the controls are in the platform, not in the agent framework.

[NOTE]
.Product status
====
Tested on OpenShift AI 3.5.2 with Connectivity Link 1.5. Connectivity Link 1.5 ships the MCP gateway as GA, including its guardrails checks on tool calls; there is no published support statement yet for that pair of versions. In OpenShift AI 3.5, MaaS external models and the MCP catalog are Technology Preview, and the MCP and agent catalogs are switched on by dashboard feature flags (`mcpCatalog`, `agentsCatalog`). Two gaps are named rather than hidden: the gateway answers a blocked tool result with HTTP 500 (the design describes an error result), and gateway-native guardrails on the *model* path are not supported in 3.5, so a thin proxy calls NeMo there.
