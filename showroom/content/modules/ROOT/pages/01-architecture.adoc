This module is the map: the application, the people, the models, and the layer that stops each scenario. Everything here is declared in Git and synced by Argo CD.

[NOTE]
.Know: why the architecture is the story
====
Nothing here is exotic. It is one ordinary insurance application with a chat assistant, deployed twice; the only difference is the platform around it. Every control maps to money: an unauthorized payout is unrecoverable spend, a shared model key with no limit is an open invoice, and an unsigned change is one nobody can account for.
====

== The application

The Parasol claims portal is a Quarkus backend with a React/PatternFly front end and a Keycloak login. It lists claims; each claim has a detail page with a timeline, a *Documents* tab and a chat panel. The chat is the agent.

Its tools come from MCP servers:

* *claims-db*: read a claim and its history, read the documents attached to it (`get_claim_documents`), propose a payout (`propose_payout`) and approve one (`approve_payout`, the write).
* *policy-docs*: read the Parasol policy documents.
* *fraud-check* (secured only): a second agent behind the same gateway that scores a claim's fraud risk.

Every tool call streams into the chat as a chip, so you see what the agent did:

* a normal chip, for example `approve_payout(CLM-1001)`;
* a red chip for a refused call, for example `403: approve_payout is not permitted for rebecca (MCP gateway)`;
* an amber banner for a guardrail detection;
* a grey `personal data masked` chip when guardrails mask personal data.

== The models

The demo uses a lean model set on an external Models-as-a-Service endpoint, reached through OpenShift AI MaaS:

* `qwen3-14b`: the agent model. *Both* portals run it. It emits structured tool calls and it obeys an instruction hidden in a document, which is what makes Scenario 2 live.
* `granite-guardian-3-1-8b`: the guard-tier detector, a model-based second opinion beside the regex detector.
* `gpt-oss-120b`: the evaluation judge in Scenario 4. It is reached with its own key, off the MaaS tiers.
* `Llama-Guard-3-1B`: an optional third detector, skipped when absent.

The agent never holds the upstream model key. OpenShift AI MaaS lists the two tiered models (`qwen3-14b` on the prod tier, `granite-guardian-3-1-8b` on the guard tier), each with its own subscription, auth policy, key and token budget.

== The secured request paths

* *Model:* portal -> model-gateway -> guardrails-proxy -> OpenShift AI MaaS -> external endpoint. The guardrails proxy scans prompts and tool results; MaaS attributes token spend to the user and enforces the per-tier budget.
* *Tools:* portal -> MCP gateway (`https://mcp.{domain}/mcp`, one virtual server per client) -> claims-db, policy-docs, fraud-check. The portal forwards the user's Keycloak token on every call; the gateway filters the tool list per identity and enforces a per-tool AuthPolicy.

The unsecured portal skips all of it: a shared model key, and tools called with no authorization and no record.

== Read, propose, act

`approve_payout` is hidden from the gateway's tool list for *every* identity, so no model can call it on its own. It stays reachable for a direct call, which is still authorized by the Keycloak role `tool:approve_payout` (claims managers only). The assistant can therefore only *propose*; a claims manager's *Approve* click performs the write, and an adjuster's forced call is a 403.

== Which layer stops which scenario

[cols="1,2,2",options="header"]
|===
|Layer |Defends |Component

|1 Isolation
|the blast radius of all scenarios
|Namespace, ResourceQuota, NetworkPolicy, restricted pod security, no service-account token

|2 Identity
|Scenario 1
|Keycloak user identity forwarded by the portal to every tool call

|3 Tool authorization
|Scenario 1
|MCP gateway (Connectivity Link): per-identity tool list, per-tool AuthPolicy

|4 Guardrails
|Scenarios 2 and 3
|Guardrails proxy (enforced): regex and prompt-injection detection, PII masking, topic refusal; Granite Guardian as a model-based detector in the guard tier

|5 Model governance
|Scenario 3
|OpenShift AI MaaS: per-tier subscriptions, auth policies, keys and token budgets enforced by Connectivity Link

|6 Lifecycle gate
|regressions and unsigned images
|Tekton pipeline (build, scan, evaluation gate, sign, verify, promote) and Sigstore admission policy

|7 Observability and control
|Scenario 3, knowing and stopping
|OpenTelemetry to Tempo and MLflow, token metrics and an alert, the kill-switch component
|===

[NOTE]
.Technology Preview status
====
As of OpenShift AI 3.5 and Connectivity Link 1.4, the MCP gateway, the MCP catalog, MaaS external-model egress and GenAI Studio guardrails are Technology Preview. Gateway-native MCP guardrails are the target design but do not yet relay tool-calling turns in this release, so the guardrails proxy is the enforced path for both Scenario 2's flag and Scenario 3's topic refusal.
