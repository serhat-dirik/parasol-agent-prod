= 09. Showcase 7: The incident, one payout reconstructed
:navtitle: 09. Showcase 7: The incident, one payout reconstructed
:toc: macro
:toclevels: 2

toc::[]

Monday morning. Finance sees a payout on CLM-1001 and asks four questions: who paid it, through what, under which rules, and was the software that did it the software that was approved? On the secured platform every answer is already on record, and each record names the next one: the claim names the person and the agent, the trace names the prompt and the model, the release names the digest, the registry names the evaluation. No one greps a laptop.

[NOTE]
.Know: an audit trail is a chain, not a log file
====
Each control writes its own record with the same keys: the user, the agent, the trace id, the prompt digest, the image digest. Follow the keys from the payout back to the release and you have reconstructed the incident from evidence the platform produced while it happened, not from what anyone remembers.
====

== The business case

[cols="1,4"]
|===
|Who
|Finance and audit asking about one payout, and the platform team that has to answer.

|What is at stake
|Accountability. Auditors and regulators ask who approved a payment, through which system, under which rules, and whether the software was the approved release. Without an evidence chain the answer is guesswork, and the payment cannot be defended.

|Without the platform
|The unsecured portal leaves a payout that says "via claims assistant" and nothing more: no person, no trace, no release record.

|With the platform
|Claim, person and agent, trace, prompt and model, release digest, evaluation: each one a platform record that names the next, with the same keys.
|===

== Before you start

This page runs on its own, in any order with the others. It needs one payout on the secured portal, made the way production makes them: a claims manager approves a proposal.

* Personas: `marcus` (claims manager, password `marcus`); an OpenShift administrator for the consoles, and the Keycloak administrator for its events.
* Create the payout: select the *Portal secured* tab, log in as `marcus`, open *CLM-1001* and send:
+
[source,text]
----
Approve the payout for this claim.
----
+
Click *Approve* on the proposal card. What you should see: the card reads "Approved by marcus via parasol-claims-agent", with a `trace <id>` link. (This is the last beat of xref:03-scenario1-colleague.adoc[03. Showcase 1]; if you just ran it, the payout already exists.)
* Headless alternative, if no browser is at hand: `scripts/abuse.sh secured marcus 1` approves CLM-1001 through the agent's token at the gateway. The claim, Keycloak, Argo CD, registry and signature steps below then work the same; the two MLflow traces of step 2 exist only for the browser path.

== Evidence demo

Five short steps, one command or one screen each, from the payout back to the release. Everything reads only. The full chain, screen by screen, is in <<Evidence details>> below.

. *Who paid, through what.* The payout record on each portal:
+
[source,bash,role=execute]
----
scripts/evidence.sh payouts CLM-1001
----
+
What you should see: `parasol-secured: PAYOUT claim=CLM-1001 amount=4200.00 previousStatus=UnderReview actor=marcus via parasol-claims-agent`. The record names the person and the agent, written by claims-db from the token on the call, not from anything the chat said.

. *Under which rules.* Live calls at the MCP gateway, then its decision log:
+
[source,bash,role=execute]
----
scripts/evidence.sh gateway
----
+
What you should see: rebecca refused `approve_payout` (HTTP 403), and in the decision log `200  marcus via parasol-claims-agent  approve_payout`: his click passed the same rule.

. *Was it the approved software?* The release run, the Argo CD pin, the running pod and the admission policy:
+
[source,bash,role=execute]
----
scripts/evidence.sh release
----
+
What you should see: the same `sha256:...` digest three times, as `PROMOTED_DIGEST` of the release run (with `EVAL_GATE passed`), as `promoted-digest` on `env-secured`, and as the running portal's `image`; then `policy.rhtas.com/include=true` and the `ClusterImagePolicy` `parasol-portal-must-be-signed` with its two accepted signers.
+
Say: what ran is what was built, evaluated and signed. Admission refuses anything else.

. *With which prompt.* The prompt the release pinned against the prompt the portal runs:
+
[source,bash,role=execute]
----
scripts/evidence.sh prompt
----
+
What you should see: the same version and the same sha256 twice. The same sha256 is the `prompt_sha256` tag on marcus's trace (next step).

. *The conversation, checked.* Click the `trace <id>` link under the approved card in the *Portal secured* tab, then open marcus's chat turn just before it (*MLflow*, *Traces*, *Filters*, field *User*, value `marcus`, the newest trace).
+
What you should see: the conversation itself (question, answer, each model call and each tool call with its arguments and result), the tags `prompt` and `prompt_sha256`, the span `tool.propose_payout`, and the *Assessments* of the AgenticOps checks. The latest checks, from the *Terminal* tab:
+
[source,bash,role=execute]
----
scripts/evidence.sh agenticops
----
+
What you should see: one line per checked turn with a finding (`user=`, `team=`, `flagged=[...]`), then `checked N new agent turns`. A clean turn has no line of its own: it was checked and nothing was flagged.

== Evidence details

For curious minds: the whole chain, one record at a time, from the payout back to the release.

. *The claim.* In the *Portal secured* tab, open *CLM-1001*, tab *History*.
+
What you should see: *Approved* "Approved by marcus via parasol-claims-agent", then *PaymentIssued*, with their times. The note was written by claims-db from the token on the call (the user and the agent), not from anything the chat said. In the *Terminal* tab:
+
[source,bash,role=execute]
----
oc logs -n parasol-secured deploy/claims-db | grep 'PAYOUT claim=CLM-1001'
----
+
What you should see: `PAYOUT claim=CLM-1001 amount=4200.00 previousStatus=UnderReview actor=marcus via parasol-claims-agent`.

. *The conversation and the click.* Click the `trace <id>` link under the approved card (or, in the *MLflow* tab, workspace `parasol-secured`, experiment `parasol-portal-chat`, *Traces*, *Filters*, field *Tags*, key `action`, value `approve_payout CLM-1001`).
+
What you should see: the approval trace: user `marcus`, tags `agent` `parasol-claims-agent` and `action` `approve_payout CLM-1001`, a `gateway.authz` span with status OK. Then open the chat turn just before it (*Filters*, field *User*, value `marcus`, the newest chat trace): tags `prompt` `parasol-claims-assistant-system-prompt/1` (the registry version behind `@production`), `prompt_sha256` (the digest of the exact prompt text that ran), `model` (the model chosen at setup), and the spans `model.chat` -> `tool.propose_payout` (proposed 4200, claimed 4200), plus any `guardrails.*` decision of that turn. The model proposed; the person approved.
+
The trace also holds the conversation itself: marcus's question as the trace's *Request*, the answer as its *Response*, the messages each model call sent and received, and each tool call's arguments and result. On the secured side every recorded text is masked with the guardrails' personal-data patterns, so the record holds no more than the model saw. Its *Assessments* tab carries the AgenticOps checks of that turn (`loop`, `excess_steps`, `unknown_tool`, `pii_in_tool_args`), logged by the CronJob `agenticops` in project `observability` within 10 minutes of the turn.
+

+
image::s9-mlflow-proposal-trace.png["MLflow, workspace parasol-secured, the marcus chat turn that proposed CLM-1001: tags agent / prompt (registry version) / prompt_sha256 / model, span tool.propose_payout selected with payout.proposed and payout.claimed"]

. *Who acted for whom.* In the Keycloak admin *private window* (page 02), realm `parasol`, *Events*, *User events*, type `TOKEN_EXCHANGE`, user `marcus`.
+
What you should see: client `parasol-claims-agent`, `username` `marcus`, `subject_token_client_id` `parasol-portal` (the browser login it acted on), `client_assertion_sub` `system:serviceaccount:parasol-secured:claims-agent` (the agent's workload identity), at the time of the approval.
+
image::s9-keycloak-exchange-marcus.png["Keycloak admin, realm parasol, Events > User events, a TOKEN_EXCHANGE row expanded just before the approval: client parasol-claims-agent, username marcus, subject_token_client_id parasol-portal, client_assertion_sub system:serviceaccount:parasol-secured:claims-agent"]

. *What the gateway decided.* Select the *OpenShift Console* tab, *Observe*, *Dashboards (Perses)*, project `openshift-operators`, *Parasol Assistant Token Spend*, row *Gateway decisions*.
+
What you should see: *Tool calls by tool, user, agent and status* with `approve_payout`, `marcus`, `parasol-claims-agent`, `200`, and in *Gateway rejections by reason* the refusals of the same period (for example rebecca's `403 role does not allow the tool`). Every gateway decision, allowed or refused, is also one line in the MCP gateway's own access log, with the user and agent Authorino verified and the tool (`oc logs -n gateway-system -l gateway.networking.k8s.io/gateway-name=mcp-gateway | grep gateway-decision`): the approval appears there as `status=200 req=[user=marcus agent=parasol-claims-agent] ... tool=approve_payout`.

. *What was live.* Select the *Argo CD* tab, application `env-secured`, *Details*, *Summary*, then *History and rollback*.
+
What you should see: the annotations `parasol.example/promoted-digest`, `promoted-by` (the release TaskRun), `prompt-ref` `...@production`, `prompt-version` (the registry version the release pinned), `prompt-sha256` and `model-ref` `parasol-claims-assistant:production`. The `prompt-sha256` is the same value as the trace's `prompt_sha256` tag: the release refuses to promote when the prompt the portal runs is not the registered one, so the prompt the trace names is literally the gated text. *History and rollback* shows the sync that rolled that digest out, before the approval time.
+
image::sc-argo-env-secured-promote.png["Argo CD, application env-secured, Summary: the annotations parasol.example/model-only-baseline, model-ref, promoted-by, promoted-digest, prompt-ref, prompt-sha256 and prompt-version written by the promote step; Synced, Healthy"]

. *Which evaluated version.* Select the *OpenShift AI* tab, *AI hub*, *Models*, tab *Registry*, `parasol-claims-assistant`, tab *Versions*, version `production`, *Properties*.
+
What you should see: `eval_gate` `passed`, an `eval_score` at or above `eval_threshold` `0.95` (0.97 in the tested runs), the `mlflow_run_id` of the golden-set evaluation and the same `prompt_sha256` again. The version `candidate-shortened` next to it failed the gate and was never promoted (xref:07-scenario5-eval-gate.adoc[07. Showcase 5]).
+
image::s9-model-registry-production.png["OpenShift AI, AI hub > Models > Registry, parasol-claims-assistant version production: eval_gate passed, eval_score 0.97, the prompt registry URI"]

. *Was it the signed image?* In the *OpenShift Console* tab, *Pipelines*, project `parasol-build`, run `parasol-portal-release-production`, tab *Details* (results).
+
What you should see: `PROMOTED_DIGEST` equal to Argo CD's `promoted-digest`, `EVAL_GATE` `passed`, `SIGNED_IMAGES` and `KEYLESS_SIGNED_IMAGES` listing `parasol-portal`; then *Workloads*, project `parasol-secured`, the `portal` pod runs exactly that digest. Admission (`ClusterImagePolicy` `parasol-portal-must-be-signed`) admitted it because the signature verified; an unsigned image is refused (xref:10-supply-chain.adoc[10. Supply chain]).

. *All of it at once.* In the *Terminal* tab:
+
[source,bash,role=execute]
----
scripts/incident-report.sh CLM-1001
----
+
What you should see: the same chain in seven read-only sections: the timeline and the PAYOUT line, the gateway's decisions in the 15 minutes before the approval (allow and deny, each with user, agent and tool), the release annotations on `env-secured`, the release run's results and the running digest. The MLflow, Keycloak and Model Registry sections print `n/a` here (the Terminal's identity may not read them; you just read them in their tabs); from a workstation with `oc` signed in as an administrator the script fills them in too. The gateway's decision lines live in the MCP gateway pod's log and are lost when that pod restarts; a production cluster ships them to cluster logging.
+
image::s9-terminal-incident-report.png["Terminal: scripts/incident-report.sh CLM-1001, sections 3 to 7: the gateway decisions before the approval (allow marcus parasol-claims-agent approve_payout), the release annotations on env-secured, the signed image and the evaluation gate 0.97"]

The point: one payout, seven independent records, joined by the same names. None of them depends on the model telling the truth.

scripts/reset.sh

The records stay, on purpose: traces, Keycloak events and logs are the audit trail, and a later reconstruction can still find this payout.
